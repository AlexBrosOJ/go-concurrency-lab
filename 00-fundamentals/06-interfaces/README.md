## 1. Интерфейс задаёт нужные методы

```go
type Namer interface {
    Name() string
}

type Renamer interface {
    Namer
    Rename(string)
}
```

Встроенный `Namer` добавляет свой метод к требованиям `Renamer`. Тип удовлетворяет интерфейсу автоматически, когда у него есть все методы с нужными сигнатурами. Функция `renameProject` может принять любой подходящий тип и пользоваться обоими методами.

| Конкретный тип | `Namer` | `Renamer` |
|---|---|---|
| `Project` | Да | Нет |
| `*Project` | Да | Да |

`Name` объявлен для получателя `Project`, а `Rename` для `*Project`. Прямой вызов `project.Rename(...)` у адресуемой переменной допустим, поскольку Go может подставить её адрес. При присваивании интерфейсу такой подстановки нет. Для `Renamer` передай `&project`. Объявления с `var _` проверяют это на этапе компиляции.

При `var named Namer = project` в интерфейс попадает копия структуры. Изменение оригинала через указатель сохраняет старое имя в копии. Если положить в интерфейс указатель, его копия будет ссылаться на тот же проект.

## 2. Динамический тип, any и проверка типа

Переменная `named` имеет статический тип `Namer`. Когда туда помещён `Project`, динамический тип равен `Project`. Форма `named.(Project)` извлекает конкретное значение. Используй два результата, когда совпадение не гарантировано:

```go
project, ok := named.(Project)
```

При несовпадении `ok` равен `false`, а `project` получает нулевое значение. Форма с одним результатом при несовпадении вызывает панику.

`any` обозначает интерфейс без требований к методам. `describe` использует `switch value := value.(type)`, чтобы отдельно описать строки, значения с методом `Name`, пустой интерфейс и остальные типы. Если конкретное поведение уже известно, узкий интерфейс позволяет вызвать его напрямую без разбора типов.

## 3. nil-указатель внутри интерфейса

```go
var pointer *Project
var empty Namer
var boxed Namer = pointer
```

`empty == nil` даёт `true`: динамический тип отсутствует. У `boxed` динамический тип `*Project` уже есть, хотя сам указатель равен `nil`. Поэтому `boxed == nil` даёт `false`. Проверка типа `boxed.(*Project)` успешна и возвращает нулевой указатель.

В примере мы не вызываем `Name` через этот указатель. Вызов метода с получателем-значением потребовал бы разыменования. Та же ловушка встречается с `error`: при успешном завершении возвращай буквальный `nil`, если сигнатура выдаёт интерфейс `error`.

## 4. io.Reader в действии

`readText` принимает `io.Reader` и через `io.ReadAll` собирает текст. В демонстрации источник создаёт `strings.NewReader`. Тест подставляет собственный источник ошибки после уже прочитанной строки. Одна и та же функция работает с обоими источниками без переключения по их типам.

Для маленького учебного текста чтение целиком удобно. При больших объёмах полезнее читать порциями или задавать предел. Ошибка чтения может прийти вместе с частичными данными. Сигнатура `readText` сохраняет оба результата.

## Что проверяют тесты

Переименование оригинала, независимость копии структуры, динамический тип нулевого указателя, пустой текст и сохранение прочитанного префикса при ошибке другого источника.

## Самопроверка

Сначала ответь самостоятельно. Затем раскрой ответ и сравни объяснение со своим.

### 1. Понимание

Какие из типов `Project` и `*Project` удовлетворяют `Namer` и `Renamer`?

<details>
<summary>Показать ответ и объяснение</summary>

Оба удовлетворяют `Namer`, поскольку метод `Name` объявлен у значения. Для `Renamer` также требуется `Rename` с получателем-указателем, поэтому подходит только `*Project`.

</details>

### 2. Вывод кода

Что напечатает этот фрагмент?

```go
var named Namer = Project{}
_, a := named.(Project)
_, b := named.(*Project)
fmt.Println(a, b)
```

<details>
<summary>Показать ответ и объяснение</summary>

`true false`. Динамический тип интерфейса — `Project`. Утверждение типа не заменяет сохранённое значение указателем при проверке.

</details>

### 3. Вывод кода

Что напечатает `fmt.Println(n == nil, p == nil)` если `p` объявлен как `var p *Project`, а `n` как `var n Namer = p`?

<details>
<summary>Показать ответ и объяснение</summary>

`false true`. В `n` сохранён динамический тип `*Project`, хотя его значение — нулевой указатель.

</details>

### 4. Типичная ошибка

Пусть `*MyError` реализует `error`. Почему у вызывающего кода проверка `err != nil` даст `true`, если функция вернула как `error` указатель `*MyError` со значением `nil`?

<details>
<summary>Показать ответ и объяснение</summary>

При преобразовании в `error` интерфейс сохраняет тип `*MyError`. На успешной ветке функция должна вернуть сам `nil`, чтобы динамический тип отсутствовал.

</details>

### 5. Понимание

Почему `readText` принимает `io.Reader`, а не `*strings.Reader`? Что делать с текстом, прочитанным до ошибки?

<details>
<summary>Показать ответ и объяснение</summary>

Функции нужен только метод `Read`, поэтому ей можно передать разные источники, в том числе тестовый. Она возвращает и префикс, и ошибку, а вызывающий код решает, годятся ли ему частичные данные.

</details>
