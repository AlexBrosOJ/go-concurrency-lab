# Ошибки в Go

## Цель

Научиться добавлять контекст к ошибкам, проверять причину и извлекать данные ошибки. Отдельный пример показывает локальную границу `panic` и `recover`. [Интерфейсы](../06-interfaces/README.md)

## Запуск

```bash
go run ./00-fundamentals/07-errors
go test -v ./00-fundamentals/07-errors
```

В примерах мы разбираем номер порта из строки. Допустимы порты от 1 до 65535. При успешном разборе результат можно использовать после проверки `err == nil`.

## 1. Одна операция и несколько причин ошибки

| Ввод | Результат разбора |
|---|---|
| `" 8080 "` | 8080 и `nil` |
| Строка из пробелов | Известная ошибка `errEmptyPort` |
| `"abc"` или число больше диапазона `int` | Ошибка `*strconv.NumError` |
| `"70000"` | `*PortRangeError` с числом 70000 |

`error` — интерфейс с методом `Error() string`. `errors.New` удобен для одной узнаваемой причины без дополнительных полей. Собственный тип `PortRangeError` позволяет сохранить ошибочное число отдельно от текста. Его метод имеет получателя `*PortRangeError`, поэтому возвращаем указатель.

## 2. Оборачивание через %w

`parsePort` добавляет к ошибке преобразования исходную строку. `loadPort` добавляет имя сервиса:

```go
return 0, fmt.Errorf("настройки сервиса %q: %w", service, err)
```

Цепочка для `"abc"` выглядит так:

```text
настройки сервиса → разобрать число → *strconv.NumError
```

`%w` сохраняет исходную ошибку для программной проверки. Вариант с `%v` перенёс бы её отображение в текст, но не сохранил бы эту связь. Решение оборачивать ошибку становится частью поведения API, если вызывающие пакеты полагаются на её причину.

## 3. errors.Is и errors.As

`errors.Is(err, errEmptyPort)` отвечает, встречается ли ожидаемая причина в возвращённой ошибке и её обёртках. Сравнение `err == errEmptyPort` в нашем примере увидит внешнюю обёртку. Поиск по тексту зависит от формулировки и плохо подходит для ветвления.

```go
var rangeErr *PortRangeError
if errors.As(err, &rangeErr) {
    fmt.Println(rangeErr.Port)
}
```

Здесь `rangeErr` имеет тип `*PortRangeError`, а `&rangeErr` даёт функции возможность заполнить эту переменную. После успешной проверки можно читать данные конкретной ошибки. Аналогично мы извлекаем `*strconv.NumError` даже через две обёртки.

## 4. panic и recover

Обычная ошибка ввода проходит через возвращаемый `error`. Для демонстрации в приватной функции `mustLoadDefaultPort` есть вариант с префиксом `must`: ошибка нарушает её ожидаемое условие, и она вызывает `panic(configPanic{...})`.

`tryDefaultPort` вызывает `recover` напрямую внутри отложенной функции. Эта функция меняет именованный результат `err` только для известного значения типа `configPanic`. Неизвестная паника передаётся дальше. После перехвата выполнение `tryDefaultPort` завершается с возвращаемыми значениями. Оно не продолжается на строке после вызова, который запаниковал.

Отложенные вызовы выполняются при выходе из функций во время раскрутки стека. `recover` действует в той же горутине. Если горутина запускает обработку с собственным договором перехвата, граница должна находиться внутри неё.

## Что увидишь при запуске

1. Корректный порт 8080.
2. Успешную проверку причины «пустой порт».
3. Число 70000 и строку `abc`, извлечённые из конкретных типов ошибок.
4. Возврат известной ошибки после локального перехвата паники.

Тесты проверяют границы допустимых портов, переполнение при разборе, сохранение причины и контекста сервиса, успешный путь и известную панику.

## Попробуй самостоятельно

1. На одном уровне замени `%w` на `%v` и сравни результаты `errors.Is` и `errors.As`.
2. Добавь поле с именем настройки в тип ошибки и извлеки его на уровне `main`.
3. Напиши функцию верхнего уровня, которая для пустого порта использует значение по умолчанию, а остальные ошибки возвращает.
4. Объясни, чем отличаются отсутствующая настройка, синтаксическая ошибка и значение вне диапазона.

## Самопроверка

Сначала ответь самостоятельно. Затем раскрой ответ и сравни объяснение со своим.

### 1. Понимание

Как выбрать между `errors.Is` и `errors.As`?

<details>
<summary>Показать ответ и объяснение</summary>

`Is` подходит для проверки известной причины, например `errEmptyPort`. `As` извлекает подходящее значение по типу, например `*PortRangeError`, чтобы потом прочитать его поле `Port`.

</details>

### 2. Вывод кода

Что напечатает `fmt.Println(port, err == nil, errors.Is(err, errEmptyPort))` после `port, err := loadPort("api", " ")`?

<details>
<summary>Показать ответ и объяснение</summary>

`0 false true`. После удаления пробелов срабатывает ошибка пустого порта. Внешняя обёртка добавляет имя сервиса и сохраняет исходную причину для `Is`.

</details>

### 3. Вывод кода

Что напечатает этот фрагмент?

```go
_, err := loadPort("api", "65536")
var portErr *PortRangeError
ok := errors.As(err, &portErr)
fmt.Println(ok, portErr.Port)
```

<details>
<summary>Показать ответ и объяснение</summary>

`true 65536`. Число разобрано успешно, но выходит за допустимый диапазон. `As` находит типизированную ошибку внутри обёртки и заполняет `portErr`.

</details>

### 4. Типичная ошибка

Почему замена `%w` на `%v` во внешней обёртке ломает поиск причины, хотя текст сообщения совпадает?

<details>
<summary>Показать ответ и объяснение</summary>

`%v` форматирует сообщение как текст. Обёртка с `%w` сохраняет исходную ошибку в цепочке, которую обходят `Is` и `As`.

</details>

### 5. Типичная ошибка

Может ли `defer` с `recover()` в `main` поймать панику, возникшую в другой горутине?

<details>
<summary>Показать ответ и объяснение</summary>

Перехват действует только в паникующей горутине и требует прямого вызова `recover` из отложенной функции. Если код устанавливает границу обработки паники, она должна быть внутри той же горутины.

</details>
