# Замыкания и общее состояние в горутинах

## Цель

Разобраться, какие данные использует запущенная функция, почему копия аргумента не всегда означает независимость памяти и как безопасно дождаться результата.

Предварительно нужны функции, слайсы, запуск горутин, `WaitGroup` и урок про гонки данных.

## Запуск из корня репозитория

```bash
go run -race ./01-goroutines/05-closures-and-shared-state
go test -count=1 -race -timeout 20s ./01-goroutines/05-closures-and-shared-state
```

Все демонстрации в `main.go` безопасны: намеренных гонок и `time.Sleep` для синхронизации нет.

## 1. Замыкание сохраняет доступ к переменной

```go
value := 10
read := func() int { return value }
value = 20
fmt.Println(read()) // 20
```

Функция не фотографирует значение в момент объявления. Она обращается к той же переменной. Для снимка создайте отдельную переменную и больше её не изменяйте. Если чтение и изменение общей переменной выполняются конкурентно без синхронизации, возникает гонка.

Вызов `go f(value)` сначала вычисляет аргумент в запускающей горутине, затем передаёт его копию функции. Это удобно для передачи чисел и индексов. Однако копия указателя по-прежнему указывает на тот же объект.

## 2. Переменные цикла: современное поведение Go

Начиная с семантики Go 1.22 переменные, объявленные циклом через `:=`, создаются отдельно для каждой итерации. Учитывается версия языка модуля в `go.mod`.

```go
for i := 0; i < 3; i++ {
    // Каждое замыкание получает свою переменную i.
}
```

Но если переменная объявлена снаружи и цикл использует `=`, она остаётся общей:

```go
var i int
for i = 0; i < 3; i++ {
    // Все замыкания обращаются к одной i.
}
```

В `main` замыкания вызываются после цикла: первый пример печатает `0, 1, 2`, второй — `3, 3, 3`. Здесь нет конкурентности, поэтому нет и гонки. Если во втором примере запустить горутины, читающие `i` одновременно с её изменением циклом, появится гонка. Даже современная семантика `:=` не защищает другие общие данные.

## 3. Независимые ячейки результатов

`squares` создаёт результирующий слайс нужной длины до запуска работников. Каждая горутина получает индекс и значение параметрами и записывает только в свою ячейку. После `Wait` вызывающий код читает готовый слайс.

Общий mutex здесь не нужен: работники обращаются к разным элементам, а заголовок слайса не меняется. Конкурентный `append` в общий слайс — другая ситуация: он изменяет заголовок и может перераспределять память, поэтому так делать без синхронизации нельзя.

Порядок выполнения работников не гарантирован, но порядок результатов соответствует входу благодаря индексам. Входной слайс нельзя конкурентно изменять во время вызова. Этот пример создаёт горутину на элемент и не подходит как есть для миллионов задач: ограничение параллелизма разберём в worker pool.

## 4. Копия слайса — не копия массива

Присваивание слайса копирует его заголовок, но не элементы backing array. Поэтому передать слайс аргументом горутины недостаточно для изоляции памяти. То же относится к map и указателям.

Для `[]int` независимую копию можно получить через `append([]int(nil), original...)` или `make` + `copy`. Для слайса указателей это будет лишь поверхностная копия: объекты по указателям всё ещё общие.

## 5. Синхронизация задаёт порядок

В демонстрации с `ready` основная горутина сначала записывает `message`, затем закрывает канал. Работник читает сообщение только после получения из закрытого канала. Такая синхронизация устанавливает необходимый порядок и видимость записи.

Канал `finished` позволяет дождаться завершения работника. Отдельный `time.Sleep` ничего не гарантирует: скорость планировщика и компьютера может меняться.

Этот пример показывает базовый механизм. Отправка, получение и закрытие каналов подробно разобраны в разделе `02-channels`.

## 6. WaitGroup не заменяет mutex

`counter++` — чтение, вычисление и запись. Несколько работников не могут безопасно выполнять эту операцию над одной переменной без защиты.

В `sharedCounter` mutex охватывает всю операцию увеличения. `WaitGroup` решает другую задачу — ожидание завершения всех работников. `Add` вызывается до запуска горутины, а `Done` отложен через `defer`.

Параметры примера — неотрицательные количества работников и увеличений. Нулевое количество даёт нулевой результат. Счётчик использует `int`, поэтому для произвольно больших значений нужно отдельно учитывать переполнение.

## Типичные ошибки

- Рассчитывать на порядок запуска горутин вместо синхронизации.
- Использовать `Sleep`, чтобы «точно дождаться» записи.
- Считать, что передача слайса или указателя копирует все данные.
- Защищать mutex только запись, оставляя чтение общего значения без защиты.
- Читать результат до `Wait`.
- Считать отсутствие отчёта `-race` доказательством безопасности всех возможных путей. Детектор проверяет только реально выполненный код.

## Практика

1. До запуска предскажите вывод каждого блока `main` и объясните его.
2. Замените квадрат в `squares` на другую операцию, сохранив порядок и независимость ячеек.
3. Добавьте вариант вычислений с возвратом результатов через канал и сравнением с `squares`.
4. В отдельном эксперименте уберите mutex у счётчика и запустите его с `-race`. Не оставляйте намеренную гонку в основном примере.
5. Сделайте слайс указателей, скопируйте его и покажите, почему копия остаётся поверхностной.
