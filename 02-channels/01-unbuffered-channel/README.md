# Небуферизированный канал

## Цель

Передать значение из одной горутины в другую без `time.Sleep` и понять, почему отправка и получение могут блокироваться. Канал здесь передаёт данные и синхронизирует две горутины.

Перед уроком нужно знать функции, запуск через `go` и то, что завершение `main` завершает программу. Начать можно с [базовой горутины](../../01-goroutines/01-basic-goroutine/README.md) и [WaitGroup](../../01-goroutines/03-waitgroup/README.md).

## Как запустить

Из корня репозитория:

```bash
go run ./02-channels/01-unbuffered-channel
go test -v -timeout 10s ./02-channels/01-unbuffered-channel
go test -race -timeout 10s ./02-channels/01-unbuffered-channel
```

Программа запускает шесть небольших примеров. Каждый вынесен в свою функцию, а `main` задаёт порядок изучения. Вывод:

```text
=== 1. One value and sender completion ===
Main: waiting for a value
Main: received 42
Main: sender finished

=== 2. Send needs a receiver ===
Send is not ready: no receiver
Received: 10

=== 3. Receive needs a sender ===
Receive is not ready: no sender
Received a real zero: 0

=== 4. Several values in order ===
Next: 10
Next: 20
Next: 30

=== 5. Request and reply ===
Square: 49

=== 6. Processing acknowledgement ===
Processed: learn channels
Main: processing confirmed
```

Перед запуском попробуй объяснить, почему последнее сообщение не появится до передачи числа.

## 1. Создание канала

```go
values := make(chan int)
```

`chan int` — канал для передачи целых чисел. `make` создаёт готовый к использованию канал. Без второго аргумента канал небуферизированный: его ёмкость `cap(values)` равна нулю, очереди для хранения значений нет.

```go
var values chan int
```

Такое объявление имеет другой смысл: это `nil`-канал. Отправка и получение через него блокируются навсегда. Для работы в примере нужен именно `make`.

## 2. Отправка и получение

```go
values <- 42     // отправить
value := <-values // получить
```

Направление стрелки помогает читать выражение: значение идёт в канал или из канала в переменную. Тип отправляемого значения должен подходить типу элементов канала.

У небуферизированного канала отправитель ждёт получателя, а получатель — отправителя. Когда обе стороны готовы, происходит передача, после которой они могут продолжить работу. Ни одна сторона не обязана начать первой.

| Ситуация | Результат |
|---|---|
| Отправка, но получателя ещё нет | Отправитель блокируется |
| Получение, но отправителя ещё нет | Получатель блокируется |
| Отправитель и получатель готовы | Передаётся одно значение |
| Получение из открытого пустого канала | Ожидание, а не возврат `0` |

Заблокированная горутина не крутится в цикле проверки; другие готовые горутины могут выполняться. Конкурентность работает и без одновременного выполнения на нескольких ядрах.

## 3. Как работает программа

В первом примере, `singleValueExample`:

1. Функция создаёт небуферизированный канал `values` и сигнальный канал `finished`.
2. `go func() { ... }()` запускает отправителя в отдельной горутине.
3. Отправитель вызывает `sendValue(values, 42)` и ждёт получения числа.
4. `main` выполняет `<-values`. После передачи в переменной `value` находится `42`.
5. После возврата из `sendValue` отправитель закрывает `finished`.
6. `main` печатает число, ждёт `<-finished` и сообщает о завершении отправителя.

Если первым дойдёт отправитель — подождёт он. Если первой дойдёт `main` — подождёт она. Правильность примера не зависит от скорости планировщика, поэтому задержки не нужны.

Получение числа подтверждает передачу, но не завершение всей функции отправителя. Именно поэтому после получения в примере есть отдельное ожидание `finished`. После передачи обе горутины продолжаются независимо: отправитель может закрыть `finished` как до, так и после печати числа в `main`.

### Примеры 2 и 3: готовность отправки и получения

В `senderWaitsExample` выполняется проверка до запуска любых получателей:

```go
select {
case values <- 10:
    fmt.Println("Unexpected: send succeeded")
default:
    fmt.Println("Send is not ready: no receiver")
}
```

`default` выполняется сразу, если ни одна операция не готова. Такая проверка не блокирует программу. Здесь отправка невозможна: канал не имеет буфера, а получателя нет. После этого запускается отправитель, и обычное `<-values` обеспечивает встречу двух сторон.

`receiverWaitsExample` делает симметричную проверку: без отправителя получение не готово. Затем горутина отправляет настоящий `0`, и получатель читает именно переданные данные. Пустой открытый канал сам нулями не заполняется.

Эти проверки показывают готовность операций в конкретный момент, а не измеряют, сколько времени горутина провела в ожидании. Полный разбор `select` будет отдельным уроком.

### Пример 4: последовательность значений

`sendValues` отправляет `10`, `20`, `30` циклом. Получатель выполняет ровно три получения:

```go
for i := 0; i < len(numbers); i++ {
    fmt.Println("Next:", <-values)
}
```

Один отправитель передаёт значения в своём порядке, и единственный получатель получает их в том же порядке. Каждая отправка отдельно встречается с получением: горутина не может заранее сложить всю последовательность в этот канал.

Получатель заранее знает количество элементов. Здесь нет `range` по каналу: он потребовал бы закрытия для завершения. Лишнее получение заблокируется, а лишняя отправка не позволит отправителю дойти до сигнала `finished`. Пустой список допустим: не будет ни отправок, ни получений.

### Пример 5: запрос и ответ

`squareOnce` принимает одно число через `requests`, вычисляет квадрат и отправляет результат через `responses`:

```go
value := <-requests
responses <- value * value
```

`main` сначала отправляет `7`, затем получает `49`. Используются два отдельных небуферизированных канала: у каждого своё направление обмена. Обработчик не сможет закончить отправку ответа, пока вызывающий код не выполнит получение.

Если обе стороны начнут с отправки и каждая будет ждать получения другой стороной, получится deadlock. Порядок «запрос → получение запроса → ответ → получение ответа» должен быть согласован. Обработчик обслуживает только один запрос; для нескольких потребуется цикл и договорённость о завершении. Квадрат вычисляется в `int` без проверки переполнения — используй небольшие числа.

### Пример 6: подтверждение обработки

`acknowledgementExample` передаёт строку через `jobs`. Получатель печатает её и только после этого отправляет `struct{}{}` через `processed`. Основная горутина ждёт подтверждение:

```go
jobs <- "learn channels"
<-processed
fmt.Println("Main: processing confirmed")
```

Первая отправка гарантирует получение строки, но не завершение печати. Вторая передача подтверждает выполнение работы до отправки сигнала. Поэтому `Processed: ...` всегда появляется раньше `Main: processing confirmed`.

В отличие от `finished`, канал `processed` не закрывается: здесь передаётся одно явное подтверждение. Сам отправитель подтверждения тоже может ещё выполнять следующие инструкции; для его завершения остаётся отдельный `finished`.

## 4. Каналы с направлением

```go
func sendValue(out chan<- int, value int) {
    out <- value
}
```

`chan<- int` разрешает отправлять значения, но запрещает читать их внутри функции. Обычный `chan int` можно передать такому параметру. Для функции, которая только читает, используется `<-chan int`.

Направление описывает доступные операции, но само по себе не определяет владельца канала. Например, канал только для отправки технически можно закрыть; договорённость о закрытии всё равно нужна.

## 5. Нужно ли закрывать канал

`close` не нужен для каждой передачи. В `values` ожидается ровно одно число, поэтому получатель знает, сколько читать; этот канал не закрывается.

`finished` используется иначе:

```go
finished := make(chan struct{})
// В горутине отправителя, после sendValue:
close(finished)
// В main:
<-finished
```

`struct{}` не несёт полезных данных. Закрытие здесь служит сигналом: дальнейшие получения из `finished` готовы сразу. Его закрывает отправитель, который знает, когда работа завершена.

Получение из закрытого канала после чтения всех значений возвращает нулевое значение и `ok == false`:

```go
value, ok := <-values
```

Само число `0` не означает закрытие: его можно передать как обычные данные. Отправка в закрытый канал и повторное закрытие вызывают панику. Подробнее закрытие и чтение через `range` будут разобраны в отдельном уроке.

## 6. Типичные ошибки

### Отправка и получение подряд в одной горутине

```go
ch := make(chan int)
ch <- 42
fmt.Println(<-ch)
```

Отправка ждёт получателя, но эта же горутина не может перейти к следующей строке. В такой самостоятельной программе runtime обнаружит deadlock. Нужна другая горутина, которая сможет получить значение.

### Обычный вызов вместо запуска горутины

```go
sendValue(values, 42)
value := <-values
```

Здесь та же проблема: `sendValue` не вернётся, пока кто-нибудь не прочитает значение. В рабочем примере отправитель запускается через `go`.

### Расчёт на time.Sleep

Задержка не создаёт получателя и не доказывает завершения передачи. Синхронизацию обеспечивают операции канала и отдельный сигнал завершения.

### Путаница между передачей и обработкой

Возврат из отправки означает, что значение принято. Получатель может ещё не выполнить вычисления, запись в файл или другую последующую работу. Если нужно дождаться её завершения, договорись об отдельном подтверждении.

## 7. Гарантии и ограничения

- Канал синхронизирует связанную с передачей работу. Записи, выполненные отправителем до отправки, видны получателю после соответствующего получения.
- Последующие изменения общих данных не становятся безопасными автоматически. Передача указателя или слайса не создаёт независимой копии всех данных; для дальнейшего совместного доступа нужна отдельная синхронизация.
- Каждый пример использует одного отправителя и одного получателя на канал. В последовательности число передач известно заранее, обработчик запросов обслуживает один запрос. Несколько получателей и распределение работы требуют отдельного разбора.
- Если убрать получателя или отправителя, соответствующая операция будет ждать. В рабочем коде нет отмены и таймаута: это тема будущих уроков про `select` и `context`.
- Таймаут в тесте ограничивает проверку, но не добавляет таймаут в `sendValue`.

## 8. Как устроены тесты

Проверяются положительное число, ноль и отрицательное число; завершение отправителя после получения; невозможность отправки без получателя и получения из пустого открытого канала без отправителя. Для последовательности проверяются пустой и `nil`-список, один элемент, порядок, повторы и отсутствие лишней передачи. Для запроса и ответа проверяются квадрат положительного и отрицательного числа, ноль и невозможность завершить обработчик до получения ответа.

Для проверок неготовых операций используется `select` с `default`: если операция сейчас невозможна, выполняется `default`. Такие проверки не требуют `Sleep`. Сам по себе немедленный просмотр сигнала завершения не доказывает, что горутина уже получила процессорное время; поэтому готовность операции отдельно проверяется через `select` на самом канале.

Вспомогательная функция `receive` ждёт значение или сигнал не более двух секунд через `time.NewTimer`. О таймауте сообщает основной поток теста. Cleanup при необходимости принимает оставшуюся отправку и ждёт завершения отправителя, тоже с ограничением времени. Внешний флаг `-timeout 10s` ограничивает весь запуск пакета, включая непредвиденные зависания.

`select` с `default` также используется в двух демонстрациях готовности операций; таймеры остаются только в тестах. Подробно изучим `select` после основ каналов.

### 1. Понимание

Когда завершается отправка в небуферизированный канал?

<details>
<summary>Показать ответ и объяснение</summary>

Когда значение принято соответствующим получением. Без получателя отправляющая горутина ждёт. Дальнейшая обработка принятого значения может ещё продолжаться.

</details>

### 2. Вывод кода

Что выведет этот фрагмент?

```go
ch := make(chan int)
go func() { ch <- 7 }()
fmt.Println(<-ch)
```

<details>
<summary>Показать ответ и объяснение</summary>

`7`. Если чтение начнётся первым, оно дождётся отправителя. Если отправка начнётся первой, она дождётся чтения.

</details>

### 3. Вывод кода

Какие три числа получит читатель, если одна горутина отправит через `sendValues` слайс `[]int{2, 0, 2}`?

<details>
<summary>Показать ответ и объяснение</summary>

`2, 0, 2` в этом порядке. Следующая отправка одной горутины начинается после предыдущей. Ноль передаётся как обычное значение.

</details>

### 4. Типичная ошибка

Почему при `ch := make(chan int)` одна горутина не сможет сначала выполнить `ch <- 7`, а потом `fmt.Println(<-ch)`?

<details>
<summary>Показать ответ и объяснение</summary>

Первая инструкция ждёт читателя, а та же горутина доберётся до чтения только после отправки. В уроке запускаем одну из сторон в отдельной горутине.

</details>

### 5. Типичная ошибка

Что изменится, если подтверждать обработку до выполнения самой работы?

<details>
<summary>Показать ответ и объяснение</summary>

Потребитель сможет получить подтверждение и продолжить слишком рано. Чтобы подтверждение означало завершение работы, отправляй его после её окончания.

</details>
