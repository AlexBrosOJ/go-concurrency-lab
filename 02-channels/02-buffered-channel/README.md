# Буферизированные каналы

## Цель

Разобраться, как ёмкость канала влияет на отправку и получение: когда горутины могут продолжать работу независимо, когда им всё равно придётся ждать и почему успешная отправка ещё не означает обработки задачи.

Предыдущий урок — [небуферизированный канал](../01-unbuffered-channel/README.md). Нужно знать `go`, отправку и получение, направления каналов и сигнал завершения через `chan struct{}`.

## Как запустить

Из корня репозитория:

```bash
go run ./02-channels/02-buffered-channel
go test -v -timeout 10s ./02-channels/02-buffered-channel
go test -race -timeout 10s ./02-channels/02-buffered-channel
```

В `main.go` семь самостоятельных примеров. Каждый вынесен в отдельную функцию; `main` задаёт порядок запуска. Везде используются каналы и явные сигналы, без `time.Sleep`.

Перед запуском предскажи, сколько отправок можно выполнить без получателя при ёмкости 2 и что произойдёт с данными после `close`.

## 1. Создание: длина и ёмкость

```go
values := make(chan int, 2)
values <- 10
values <- 20
```

Второй аргумент `make` задаёт ёмкость — число значений, которые канал может хранить. Эти две отправки можно выполнить в одной горутине без получателя: оба значения помещаются в буфер.

- `cap(values)` — ёмкость, здесь всегда `2`.
- `len(values)` — число значений, находящихся сейчас в буфере.
- После двух отправок длина равна `2`; после одного получения — `1`.
- Получение освобождает место, но не уменьшает ёмкость.

Ёмкость фиксируется при создании: канал не растёт автоматически как слайс. Отрицательная ёмкость недопустима. `make(chan int, 0)` создаёт небуферизированный канал и эквивалентен `make(chan int)`. Оба отличаются от `var ch chan int`, где канал равен `nil`.

В `capacityExample` нет других горутин, поэтому значения `len` воспроизводимы. В конкурентной программе длина — только моментальный снимок: другая горутина может изменить её сразу после проверки.

## 2. FIFO: порядок значений

`fifoExample` отправляет строки `first`, `second`, `third`, а затем получает их в том же порядке.

FIFO означает «первым пришёл — первым вышел». Уже поставленные в очередь значения не переставляются. Один отправитель и один получатель сохраняют последовательность отправок.

Несколько конкурентных отправителей могут приходить к операции в разном порядке: по исходному коду нельзя предсказать общий порядок их значений. При нескольких получателях также не гарантирован порядок завершения обработки или печати результатов.

## 3. Полный буфер и освобождение места

```go
values := make(chan int, 2)
values <- 10
values <- 20
```

Теперь буфер полон. В `fullBufferExample` проверка через `select` показывает, что третья отправка пока невозможна:

```go
select {
case values <- 30:
    fmt.Println("Unexpected: send succeeded")
default:
    fmt.Println("Buffer full: send is not ready")
}
```

`default` выполняется сразу, если ни одна операция не готова. Третье значение здесь **не отправлено**. Обычное `values <- 30` вместо этой проверки заблокировало бы горутину: в данном примере нет другого получателя, который мог бы освободить место.

После `<-values` извлекается `10`, появляется свободное место, и отправка `30` проходит. Оставшиеся значения — `20`, затем `30`.

В общей конкурентной программе полный буфер не означает, что отправка обязательно будет долго ждать: получатель может немедленно прочитать элемент и освободить место. Наш пример проверяет состояние, когда других участников ещё нет.

## 4. Пустой буфер

Наличие ёмкости не создаёт значений. Получение из пустого открытого канала ждёт отправителя, как и у небуферизированного канала.

В `emptyBufferExample` `select` сначала выбирает `default`. Затем в канал отправляется настоящий `0`, и получение возвращает его.

| Состояние открытого канала | Отправка | Получение |
|---|---|---|
| Пустой буфер с положительной ёмкостью | Может поместить значение в буфер | Ждёт значение |
| В буфере есть значения и свободные места | Может добавить значение | Может извлечь значение |
| Буфер полон | Ждёт освобождения места | Может извлечь значение |

Операция, которая ждёт, блокирует текущую горутину, а не все остальные. Таблица описывает готовность в данный момент; другие участники могут изменить состояние канала.

## 5. Производитель и потребитель

В `producerConsumerExample` отправляются пять чисел при ёмкости 2:

```go
go func() {
    defer close(finished)
    sendValues(values, numbers)
}()
```

`sendValues` выполняет обычные блокирующие отправки в цикле. Первые значения могут попасть в буфер заранее. Когда мест больше нет, производитель ждёт; потребитель получает очередное число, освобождая место для продолжения.

Это обратное давление: потребитель ограничивает скорость продвижения производителя, когда буфер заполнен. Вместо бесконечного накопления очередь имеет предел.

Получатель знает количество чисел и делает ровно столько получений. После этого он отдельно ждёт `finished`: получение последнего числа само по себе не гарантирует, что производитель уже выполнил инструкции после последней отправки.

Из-за планирования нельзя обещать, что производитель непременно успеет заполнить буфер до начала чтения. Порядок чисел при этом сохраняется. В примере печатает только потребитель, поэтому вывод воспроизводим.

## 6. Закрытие и чтение оставшихся значений

В `closeAndDrainExample` в канал сначала помещаются `0` и `42`, затем он закрывается:

```go
values <- 0
values <- 42
close(values)
```

Закрытие сообщает, что новых значений больше не будет. Уже переданные значения сохраняются и доступны для чтения в прежнем порядке.

```go
for value := range values {
    fmt.Println("Drained:", value)
}
```

`range` по каналу получает значения до его закрытия и опустошения. Если канал оставить открытым, цикл после чтения всех значений будет ждать продолжения. Здесь закрытие произошло до цикла, поэтому он гарантированно завершится.

После чтения всего буфера:

```go
value, ok := <-values // 0, false
```

У сохранённого в буфере `0` было бы `ok == true`. После опустошения закрытый канал каждый раз возвращает нулевое значение и `false` без ожидания.

Отправка в закрытый канал вызывает панику даже при наличии свободных мест. Повторный `close` тоже вызывает панику. Получатель обычно не закрывает канал: решение принимает сторона, которая знает, что все отправки завершены. В этом примере отправитель и получатель — одна горутина.

Закрытие не требуется для освобождения памяти и не является отменой уже начавшейся обработки. Более сложное владение каналами разберём в отдельном уроке о закрытии и `range`.

## 7. Поставлено в очередь — ещё не обработано

`queuedIsNotProcessedExample` использует канал задач с ёмкостью 1 и два сигнальных канала:

- `allowProcessing` — разрешение начать обработку;
- `finished` — подтверждение завершения работы обработчика.

Обработчик сначала ждёт разрешение. Основная горутина тем временем успешно выполняет отправку:

```go
jobs <- "learn buffered channels"
```

Задача помещается в буфер, хотя обработчик ещё не начал чтение. Поэтому сразу после отправки нельзя утверждать, что задача уже получена или выполнена.

Затем основная горутина закрывает `allowProcessing`, обработчик получает задачу и печатает результат. Только после получения сигнала `finished` можно сообщить о завершении работы.

Это явный порядок событий, а не предположение о том, что обработчик «достаточно медленный». Длительность задержки или скорость компьютера на правильность примера не влияют.

## Сравнение с небуферизированным каналом

| Свойство | Без буфера | С буфером |
|---|---|---|
| Создание | `make(chan int)` | `make(chan int, n)`, где `n > 0` |
| Отправка без готового получателя | Ждёт получения | Может завершиться, если есть место |
| Что подтверждает возврат из отправки | Значение принято получателем | Значение передано каналу; получатель мог его ещё не прочитать |
| Получение без готового отправителя | Ждёт отправки | Может прочитать ранее сохранённое значение |
| Ожидание обработки | Нужно отдельное подтверждение | Нужно отдельное подтверждение |

Оба вида каналов синхронизируют передачу данных. Записи отправителя до отправки доступны получателю после соответствующего получения. Но возврат из буферизированной отправки не подтверждает выполнение кода получателя. Передача указателя или слайса также не делает дальнейшие совместные изменения безопасными автоматически.

## Типичные ошибки и ограничения

- **Бесконечно увеличивать буфер.** Большая очередь удерживает больше данных и может увеличить время ожидания задачи. Если производитель постоянно быстрее потребителя, заполнится и большой буфер.
- **Проверять `len(ch) < cap(ch)` перед отправкой.** В конкурентном коде между проверкой и отправкой другой участник может занять место. Для попытки отправки без ожидания используй `select` с `default` и явно реши, что делать при отказе. Не теряй задачи молча.
- **Считать буфер исправлением deadlock.** Он может лишь отложить блокировку до заполнения. Если обе стороны ждут действия, до которого никто не может дойти, нужно менять протокол обмена.
- **Считать ёмкость числом обработчиков.** Буфер ограничивает очередь значений, но не создаёт воркеров и не задаёт число одновременно выполняемых операций.
- **Считать буфер rate limiter.** Ёмкость не задаёт число запросов в секунду.
- **Прекратить чтение раньше времени.** Производитель может остаться заблокированным. В `sendValues` нет отмены; потребитель обязан получить все ожидаемые значения. Отмена через `context` будет отдельной темой.
- **Полагаться на конкретное распределение между горутинами.** Буфер не гарантирует равномерности, справедливого обслуживания или общего порядка конкурентных отправителей.

## Что проверяют тесты

- Ёмкости 1, 2 и 5: отправки без получателя, заполнение и FIFO.
- Неготовность отправки в полный буфер и получения из пустого открытого канала.
- Повторное использование места после получения.
- Отправку последовательности: пустой и `nil`-список, повторы, ноль, отрицательные числа, вход длиннее буфера, вход короче буфера и ёмкость 0.
- Сохранение порядка, отсутствие лишних значений и завершение производителя.
- Чтение всех значений после закрытия, различие между переданным нулём и закрытым опустошённым каналом, закрытие пустого буфера.

Ожидания отправки и получения ограничены таймером в две секунды. Cleanup при раннем завершении теста дочитывает канал, чтобы освободить производителя; у самого cleanup также есть таймаут. `select` с `default` проверяет неготовность операций без `Sleep`. Общий флаг `-timeout 10s` дополнительно ограничивает весь запуск пакета.

Таймауты тестов не добавляют отмену в учебную функцию. Примеры намеренных deadlocks приведены в объяснении; рабочая программа и тесты должны завершаться.

Сначала ответь самостоятельно. Затем раскрой ответ и сравни объяснение со своим.

### 1. Понимание

Чем `len(ch)` отличается от `cap(ch)`?

<details>
<summary>Показать ответ и объяснение</summary>

`len` показывает число значений, находящихся в буфере в момент вызова. `cap` показывает неизменную ёмкость. Другие горутины могут изменить заполненность сразу после проверки.

</details>

### 2. Вывод кода

Что напечатает этот фрагмент?

```go
ch := make(chan int, 2)
ch <- 10
ch <- 20
fmt.Println(<-ch)
ch <- 30
fmt.Println(<-ch, <-ch)
```

<details>
<summary>Показать ответ и объяснение</summary>

Сначала `10`, затем `20 30`. Первое чтение освобождает слот, а новые значения добавляются после уже стоящих в очереди.

</details>

### 3. Вывод кода

В `ch := make(chan int, 1)` отправили ноль, затем закрыли `ch`. Какие значения получат `v` и `ok` сначала после `v, ok := <-ch`, а затем после `v, ok = <-ch`?

<details>
<summary>Показать ответ и объяснение</summary>

Сначала `0, true`: это настоящий ноль из буфера. Затем `0, false`: закрытый канал уже опустел.

</details>

### 4. Типичная ошибка

Почему проверка `if len(ch) < cap(ch)` не гарантирует неблокирующую отправку в конкурентном коде?

<details>
<summary>Показать ответ и объяснение</summary>

Между проверкой и отправкой другой работник может занять свободное место. Если канал гарантированно не закроется во время попытки, `select` с `default` позволяет не ждать свободного места. От паники при отправке в закрытый канал `default` не защищает.

</details>

### 5. Типичная ошибка

Может ли производитель считать задачу выполненной сразу после отправки в буфер?

<summary>Показать ответ и объяснение</summary>

Значение могло только занять место в очереди. Для подтверждения обработки нужен отдельный результат или сигнал от работника.

</details>
