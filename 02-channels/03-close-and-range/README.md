# Закрытие каналов и range

## Цель

Научиться завершать потоки данных, длина которых заранее неизвестна получателю. Разберём, кто закрывает канал, как отличить данные от конца потока, как дождаться нескольких производителей и что означает закрытие для нескольких получателей.

Предыдущие уроки: [небуферизированный канал](../01-unbuffered-channel/README.md) и [буферизированные каналы](../02-buffered-channel/README.md). Для примера с несколькими производителями понадобится [WaitGroup](../../01-goroutines/03-waitgroup/README.md).

## Как запустить

Из корня репозитория:

```bash
go run ./02-channels/03-close-and-range
go test -v -timeout 10s ./02-channels/03-close-and-range
go test -race -timeout 10s ./02-channels/03-close-and-range
```

В `main.go` восемь примеров, каждый в отдельной функции. Нет `time.Sleep`: завершение обеспечивают закрытие, каналы результатов и `WaitGroup`. Последний пример намеренно вызывает три паники и перехватывает каждую локально, чтобы программа продолжила выполнение.

Перед запуском ответь на два вопроса: что прочитает получатель после `close`, если в буфере остались данные, и кто должен закрывать общий канал двух производителей?

## 1. Конечный поток неизвестной длины

Функция `stream` возвращает канал только для чтения:

```go
func stream(values []int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for _, value := range values {
            out <- value
        }
    }()
    return out
}
```

Она сразу возвращает канал; отправки выполняет отдельная горутина. Единственный производитель отправляет все значения и закрывает выход. `defer` привязывает закрытие к выходу из функции производителя, в том числе при возможном раннем `return`.

Получателю не нужно знать число элементов:

```go
for value := range stream([]int{10, 20, 30}) {
    fmt.Println("Received:", value)
}
```

`range` ждёт очередное значение, а не проверяет только текущий размер очереди. Он заканчивается, когда канал закрыт и все переданные значения прочитаны. У небуферизированного канала нет очереди, но правило завершения то же.

Здесь два разных `range`: `range values` у производителя перебирает слайс; `range out` у потребителя получает значения из канала и ждёт завершения потока.

## 2. Два результата получения: value и ok

```go
value, ok := <-values
```

- `ok == true` — получено реально отправленное значение, включая ноль.
- `ok == false` — канал закрыт, значений для получения больше нет; `value` содержит нулевое значение типа.

`commaOKExample` помещает в буфер `0` и `42`, закрывает канал, затем выполняет четыре получения:

```text
Read 1: value=0 ok=true
Read 2: value=42 ok=true
Read 3: value=0 ok=false
Read 4: value=0 ok=false
```

Закрытие не удаляет накопленные данные. После их чтения получение остаётся готовым и снова возвращает `0, false`. Поэтому такой цикл неверен для определения конца потока:

```go
for {
    value := <-values
    fmt.Println(value)
}
```

После опустошения закрытого канала он будет бесконечно печатать нули. Используй `range` или явную проверку `ok`:

```go
for {
    value, ok := <-values
    if !ok {
        break
    }
    fmt.Println(value)
}
```

`range` скрывает проверку `ok`, но не возвращает фиктивный ноль в последней итерации. При обходе канала есть только одна переменная итерации — само значение, без индекса.

## 3. Пустой закрытый канал

`emptyStreamExample` передаёт в `stream` пустой список. Производитель не делает ни одной отправки и закрывает выход. Цикл получателя выполняет ноль итераций.

Важно различать:

| Состояние | Получение | range |
|---|---|---|
| Открытый пустой канал | Ждёт значение или закрытие | Ждёт следующую итерацию |
| Закрытый канал с данными в буфере | Возвращает данные с `ok == true` | Продолжает получать данные |
| Закрытый опустошённый канал | Возвращает нулевое значение и `false` | Завершается |
| `nil`-канал | Блокируется навсегда | Блокируется навсегда |

`len(ch) == 0` не означает конец потока. Канал может быть открытым, а новое значение появится позже. У небуферизированного канала `len` вообще всегда равен нулю.

## 4. Обработка всего потока

`sum(in <-chan int)` суммирует значения до закрытия входа:

```go
func sum(in <-chan int) int {
    total := 0
    for value := range in {
        total += value
    }
    return total
}
```

Она не создаёт горутину самостоятельно: вызывающий код решает, где выполнять обработку. В `sumExample` производитель работает в фоне, а `sum` — в основной горутине.

Сумма пустого потока — `0`. Если вход никогда не закроется, `sum` не вернётся, даже если все уже отправленные значения прочитаны. Арифметика использует `int` без проверки переполнения; для упражнений достаточно небольших чисел.

## 5. Несколько производителей и один владелец закрытия

В `sharedStream` несколько горутин отправляют значения в **один общий канал**. Каждой группе входных чисел соответствует один производитель.

Правильный порядок:

1. Создать канал и зарегистрировать всех производителей через `wg.Add` до их запуска.
2. Каждому производителю поручить отправки и `defer wg.Done()`.
3. Отдельной горутине дождаться `wg.Wait()`.
4. Только после этого закрыть общий выход.

```go
go func() {
    wg.Wait()
    close(out)
}()
```

Если каждый производитель будет закрывать общий канал самостоятельно, первый завершившийся может закрыть его, пока другой ещё отправляет. Получится паника; повторное закрытие тоже недопустимо.

Здесь владелец закрытия — координатор. Он не отправляет данные сам, но знает, когда **все** отправки закончились. Правило «закрывает отправитель» точнее понимать так: решение принадлежит стороне, которая контролирует завершение всех отправок.

При отсутствии производителей счётчик сразу нулевой, и выход закроется без данных. Производители с пустыми группами тоже допустимы. Глобальный порядок нескольких производителей не фиксирован; пример печатает только количество и сумму, не зависящие от перемешивания.

Связь с [fan-in](../../03-concurrency-patterns/01-fan-in/README.md): там есть отдельный входной канал на источник и горутина пересылки для каждого входа. Здесь производители сразу пишут в один общий канал. В обоих случаях выход закрывает один координатор после завершения всех отправок.

## 6. Несколько получателей

`multipleConsumersExample` запускает два вызова `sum` на одном входе. Каждое переданное число получает **один** из обработчиков, а не оба. Канал распределяет данные, не копируя поток каждому участнику.

После закрытия и опустошения канала оба цикла закончатся. Частичные суммы отправляются в канал результатов; основная горутина получает ровно два результата и складывает их.

Нельзя обещать равномерного распределения: один обработчик может получить все числа, другой — ни одного. Суммарный результат всё равно равен `21`. Мы не выводим частичные суммы, чтобы пример не создавал ложного ожидания конкретного распределения.

Канал результатов имеет ёмкость 2 — по одному сообщению от обработчика. Его не нужно закрывать ради этих двух получений: число результатов заранее известно. Если бы результаты читались через `range`, для завершения потребовалось бы организовать закрытие.

## 7. Закрытие как сигнал для всех

Данные из канала распределяются между получателями, но закрытие видят все:

```go
done := make(chan struct{})
go func() {
    <-done
    // Сигнал получен.
}()
close(done)
```

Получение из закрытого пустого `done` готово для любого числа горутин, включая те, которые начнут ждать после закрытия. Это удобно для одноразового сигнала о событии.

В `broadcastExample` запускаются три слушателя. Каждый после получения сигнала отправляет подтверждение в `acknowledged`. Основная горутина закрывает `done`, затем ждёт три подтверждения.

Закрыть `done` — не то же самое, что дождаться слушателей: им ещё нужно получить процессорное время и выполнить свою работу. Именно поэтому есть отдельный сбор подтверждений. Одна отправка `done <- struct{}{}` разбудила бы одного получателя; закрытие делает получение готовым для всех.

Закрытие — необратимое событие: такой канал нельзя «открыть обратно». Для нового независимого события нужен новый канал.

## 8. Недопустимые операции

Последний пример показывает три ошибки:

| Операция | Результат |
|---|---|
| Отправка в закрытый канал | Паника, даже если в буфере есть место |
| Повторное закрытие | Паника |
| Закрытие `nil`-канала | Паника |
| Получение из закрытого канала | Допустимо |
| Отправка или получение через `nil` | Блокировка, не паника |

`showPanic` перехватывает каждую демонстрационную панику через `defer` и `recover`, печатает сообщение и возвращает управление. Перехват выполняется в той же горутине, где вызвана ошибочная операция. `recover` в `main` не перехватит панику другой горутины.

В рабочем коде не следует маскировать ошибки владения с помощью `recover`. Нужно организовать один момент закрытия и исключить дальнейшие отправки. Даже `sync.Once` защищает лишь от повторного `close`, но не делает одновременные отправку и закрытие безопасными.

## Типичные ошибки и ограничения

### Выйти из range раньше, чем закончился производитель

```go
for value := range stream([]int{1, 2, 3}) {
    fmt.Println(value)
    break
}
```

`break` завершает только цикл получателя. Он не отменяет производителя и не закрывает канал. Производитель может зависнуть на следующей отправке, не дойти до `defer close(out)` и остаться в памяти вместе со своими данными.

В этом уроке `stream` и `sharedStream` требуют дочитывания. Для досрочного выхода нужно спроектировать отдельную отмену и учитывать её при отправках, например через `context` и `select`. Сам по себе буфер лишь может отложить проблему.

### Проверять, закрыт ли канал, перед отправкой

В Go нет безопасной универсальной проверки «закрыт ли канал» для последующей отправки: между проверкой и отправкой другая горутина может вызвать `close`. Чтение с `ok` также потребляет данные, а не просто исследует состояние. Решение — протокол владения и координация, а не предварительная проверка.

### Считать close ожиданием всех обработчиков

Закрытие сообщает об окончании отправок, но не ждёт обработки уже полученных значений. Даже завершение `range` одного получателя не означает завершение работы других получателей. Для этого нужны результаты, подтверждения или `WaitGroup`.

### Закрывать канал ради освобождения памяти

Закрытие нужно для протокола обмена, а не как аналог `free`. Если никто больше не использует канал и на нём нет зависших участников, сборщик мусора может освободить его и без `close`. Закрывать каждый канал обязательно не требуется.

### Игнорировать неизменность входных данных

`stream` и `sharedStream` читают переданные слайсы из фоновых горутин без копирования. Вызывающий код не должен менять их элементы во время этих чтений. Канал не делает конкурентную работу с исходным слайсом безопасной автоматически.

## Что проверяют тесты

- Конечный поток: `nil`-список, пустой список, одно значение, ноль, отрицательные числа, повторы и порядок одного производителя.
- Реальный `range` внутри `sum`: завершение на закрытом пустом канале и обработка всех накопленных значений.
- Несколько производителей: отсутствие производителей, пустые группы, группы разной длины и сохранение повторов. Результат сравнивается после сортировки, без требования общего порядка.
- Отличие реально переданного нуля от конца потока и повторное получение из закрытого опустошённого канала.
- Паники при отправке после закрытия, повторном закрытии и закрытии `nil`.

Сбор потока ограничен **одним** таймером в две секунды на все значения и ожидание закрытия. `sum` запускается в горутине, результат которой также ожидается с таймаутом. При раннем выходе из проверки cleanup дочитывает поток, освобождая производителей; ожидание cleanup тоже ограничено. Глобальный `-timeout 10s` служит дополнительным пределом всего запуска пакета.

Таймаут теста не добавляет отмену в учебную функцию. Если дефект не позволяет производителю завершиться даже после cleanup, тест сообщит об этом; универсально остановить произвольную горутину таймером нельзя.

2. Напиши `count(in <-chan int) int` и проверь пустой поток, повторы и несколько значений.
3. Добавь третьего производителя, включая пустую группу. Почему место закрытия остаётся прежним?

5. Замени закрытие сигнала в седьмом примере одной отправкой. Сколько слушателей сможет её получить? Не запускай оставшихся без плана завершения.
6. Объясни, почему `defer close(out)` не спасает производителя, если получатель ушёл раньше и отправка заблокировалась.
7. Добавь буфер к `stream`. Какие гарантии сохраняются и почему буфер не заменяет отмену?
8. Спроектируй поток с возможностью досрочного завершения. Какие участники должны знать об отмене и какие операции могут блокироваться?
