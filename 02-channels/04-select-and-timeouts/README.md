# Select и таймауты

## Цель

Научиться ждать несколько операций с каналами, выполнять попытку без ожидания, ограничивать время отправки и получения и завершать пересылку по отдельному сигналу.

Предыдущий урок — [закрытие каналов и range](../03-close-and-range/README.md). Нужно понимать буферы, `value, ok`, владельца закрытия и различие между передачей значения и завершением работы.

## Как запустить

Из корня репозитория:

```bash
go run ./02-channels/04-select-and-timeouts
go test -v -timeout 10s ./02-channels/04-select-and-timeouts
go test -race -timeout 10s ./02-channels/04-select-and-timeouts
```

В `main.go` девять примеров. Задержек через `Sleep` нет: три примера намеренно ждут таймер по 10 миллисекунд. Фактическое ожидание может оказаться дольше из-за планирования и нагрузки; точную длительность программа не проверяет.

## 1. Select выбирает одну готовую операцию

```go
select {
case value := <-first:
    fmt.Println("Selected:", value)
case value := <-second:
    fmt.Println("Selected:", value)
}
```

`select` рассматривает операции отправки и получения. Если готова одна, выполняется она и тело её ветки. Если готовы несколько, выбирается одна из готовых веток псевдослучайно с равномерным выбором среди них. Положение ветки сверху не задаёт приоритета.

`readyCasesExample` заранее помещает по строке в два буферизированных канала. Поэтому в выводе допустимы `Selected: first` и `Selected: second`. За один вход в `select` читается только один канал, второе значение остаётся в другом.

Если ни одна операция не готова и `default` отсутствует, текущая горутина блокируется до появления готовой операции. Остальные горутины могут продолжать работу.

У `select` нет автоматического повторения: для нескольких событий нужен внешний цикл. Обычный `break` внутри `select` прекращает его, а не обязательно внешний `for`. Для выхода из функции используй `return`, для выхода из именованного цикла — `break` с меткой.

## 2. Default: попытка без ожидания

```go
select {
case value := <-values:
    fmt.Println(value)
default:
    fmt.Println("Nothing ready")
}
```

`default` выполняется, если ни одна операция сейчас не готова. Он не соревнуется с готовыми ветками и не является таймером.

В `defaultExample` канал открыт и пуст, отправителя нет, поэтому программа сразу продолжает работу без получения. Если значение появится через мгновение после выбора `default`, эта попытка его не получит.

Не делай бесконечный `for` с пустым `default` ради ожидания: он может занять процессор постоянными проверками. Для ожидания убери `default` или добавь осмысленное событие, например таймер или отмену.

## 3. Отправка тоже может быть case

```go
select {
case values <- 42:
    // Передача состоялась.
default:
    // Передача не состоялась.
}
```

В `selectSendExample` канал имеет одно свободное место, поэтому отправка готова. Если буфер был бы полон и получателя не было, выполнился бы `default`.

Не заменяй эту конструкцию проверкой `len(ch) < cap(ch)`: другая горутина может занять место между проверкой и отправкой. При выборе `default` нужно явно решить судьбу задачи — повторить позже, вернуть ошибку или допустимо пропустить; молчаливая потеря не универсальное решение.

Выражения каналов и значения для отправки вычисляются при входе в `select`, даже если их ветка не будет выбрана. В `case out <- expensiveCalculation():` вычисление может произойти и при последующем выборе `default`. Учитывай стоимость и побочные эффекты таких выражений.

## 4. Значение, закрытие и таймаут — разные исходы

Функция `receiveWithin` возвращает три результата:

```go
func receiveWithin(in <-chan int, timeout time.Duration) (int, bool, error)
```

| Исход | value | ok | err |
|---|---|---|---|
| Получено значение | Отправленное число | `true` | `nil` |
| Канал закрыт и опустошён | `0` | `false` | `nil` |
| Истекло время ожидания | `0` | `false` | `errTimeout` |

Сначала проверяй `err`, затем `ok`; только после этого используй число. Само `0` не означает ни ошибку, ни закрытие.

```go
timer := time.NewTimer(timeout)
defer timer.Stop()
select {
case value, ok := <-in:
    return value, ok, nil
case <-timer.C:
    return 0, false, errTimeout
}
```

В `receiveAndCloseExample` канал содержит настоящий `0` и уже закрыт. Первое получение вернёт `0, true, nil`, второе — `0, false, nil`. Оба готовы без ожидания таймера.

## 5. Таймаут получения

В `receiveTimeoutExample` вход равен `nil`. Его ветка отключена, поэтому сработает только таймер. Это позволяет показать таймаут без оставленной фоновой горутины.

Так же будет вести себя открытый пустой канал, если за время ожидания никто не отправит значение и не закроет его.

`time.NewTimer` создаёт одноразовый таймер. При наступлении срока его канал становится готов к получению. `Stop` останавливает ещё не сработавший таймер, когда операция закончилась раньше; он не закрывает `timer.C`. Из возвращаемого `Stop` значения нельзя делать вывод о завершении чужой работы.

Текущий пример не переиспользует таймер через `Reset` и не требует дренировать канал для повторного запуска. Здесь таймер создаётся на один вызов функции.

Нулевая или отрицательная длительность делает таймер готовым без положительного ожидания. Но если данные тоже готовы, обычное правило выбора между готовыми ветками остаётся: нулевой таймаут не задаёт приоритет таймеру. Для строгой попытки «прямо сейчас» используй `select` с `default`.

## 6. Таймаут отправки

`sendWithin` ограничивает время ожидания отправки тем же способом. В `sendTimeoutExample` буфер ёмкости 1 уже содержит `10`, получателя нет. Попытка отправить `20` заканчивается `errTimeout`, а исходное `10` остаётся в канале.

Если выбран таймер, эта операция отправки не выполняется и позже сама не возобновится. Повторять её или нет — решение вызывающего кода.

Успех буферизированной отправки означает передачу каналу, а не выполнение задачи. Кроме того, `select` не защищает от отправки в закрытый канал: такая отправка может вызвать панику. Владение каналом и согласование закрытия остаются обязанностью участников.

## 7. time.After для одноразового ожидания

```go
select {
case value := <-values:
    fmt.Println(value)
case <-time.After(10 * time.Millisecond):
    fmt.Println("Waiting ended")
}
```

`time.After` удобно, когда нужен только канал одноразового таймера и не нужен явный `Stop`. В примере вход `nil`, поэтому исход однозначен.

Не создавай `time.After(timeout)` заново при каждой итерации цикла, если нужен общий предел времени всей операции: это будет новый срок на каждой итерации. Для общего бюджета создай один таймер перед циклом. Для таймаута бездействия между событиями нужен другой договорённый алгоритм и аккуратная работа с переустановкой таймера.

Таймеры не бесплатны: создание таймера на каждой итерации может давать лишние выделения и работу runtime. В этом уроке используем одноразовые таймеры без сложной оптимизации.

## 8. Закрытый вход нужно отключать

Закрытый опустошённый канал всегда готов к получению. Если оставить его в цикле `select`, можно бесконечно читать нули с `ok == false`, тратить процессор и мешать полезной обработке.

В `mergeUntilDone` после конца каждого входа локальная переменная заменяется на `nil`:

```go
case value, ok = <-first:
    if !ok {
        first = nil
        continue
    }
```

`nil`-канал не закрыт: его операции просто никогда не готовы. Ветка отключается. Когда оба входа стали `nil`, условие цикла завершается, и единственный координатор закрывает выход.

Локальное присваивание `first = nil` не закрывает канал и не меняет переменную вызывающего кода. Входы принадлежат их производителям; `mergeUntilDone` закрывает только созданный ею `out`.

Порядок значений каждого отдельного входа сохраняется; общий порядок двух входов не фиксирован. Поэтому пример печатает число элементов и сумму: `count=4 sum=10`.

Особый случай: если оба аргумента входов сразу `nil`, функция сразу закроет выход — так определён её контракт. Она не будет ждать `done` при отсутствии активных источников.

## 9. Таймаут ожидания не равен отмене работы

Если получатель вышел по таймауту, производитель может продолжать вычислять или ждать отправки. Функции `receiveWithin` и `sendWithin` ограничивают одну операцию, не управляя жизненным циклом других участников.

Для кооперативной остановки `mergeUntilDone` принимает канал `done`. Его закрывает сторона, которая управляет отменой. Горутине пересылки нужно учитывать отмену **в обеих точках ожидания**:

1. При чтении входов.
2. При отправке в выход, если потребитель перестал читать.

```go
select {
case out <- value:
case <-done:
    return
}
```

Если добавить отмену только к чтению, горутина может получить число и навсегда заблокироваться на следующей обычной отправке.

`cancellationExample` закрывает `done`, пока выход ещё никто не читает. Пересылка завершится и закроет свой выход, даже если вход открыт и пуст или значение уже ожидает передачи дальше. В примере нет внешних фоновых производителей, которых можно было бы оставить заблокированными.

Отмена не имеет встроенного приоритета над данными. Если `done` закрыт и отправка одновременно готова, может быть выбрана отправка. Не обещай, что после отмены не пройдёт ни одного готового значения. Для более строгих требований нужен отдельно спроектированный протокол.

Пересылка не закрывает чужие входы и не останавливает внешних производителей автоматически. В реальной системе они тоже должны знать об отмене. Позже перенесём этот подход на `context.Context` с дедлайнами и распространением отмены.

```text

=== 3. A send case ===
```

В первом примере также допустимо `Selected: second`. Ни тесты, ни объяснение не требуют выбора конкретной ветки или точного числа миллисекунд ожидания.

## Типичные ошибки

- Поставить `default` рядом с таймером и ожидать задержку: если ничего не готово, `default` выполнится сразу.
- Считать верхнюю ветку приоритетной или требовать выбора отмены при одновременно готовых данных.
- Создавать новый таймер в цикле вместо одного общего срока.
- Забыть проверку `ok` и продолжать читать закрытый канал.
- Выйти по таймауту, оставив производителя на блокирующей отправке.
- Обрабатывать отмену только при чтении, но не при отправке.
- Запустить пустой `select {}` без других способов продолжения: он блокирует текущую горутину навсегда.
- Думать, что таймер прерывает выполняющуюся функцию. `select` реагирует, когда управление находится в нём; длительное вычисление внутри выбранной ветки само не остановится.

## Что проверяют тесты

- Получение числа, нуля, отрицательного числа; закрытый пустой и закрытый заполненный вход.
- Таймаут на `nil` и пустом открытом входе; нулевая и отрицательная длительность без готовых данных.
- Успешную отправку и таймаут на полном, `nil` и небуферизированном выходе без получателя. При таймауте данные не отправляются позже.
- Объединение отсутствующих, закрытых, пустых и непустых входов, повторов и отрицательных значений; общий результат сравнивается без требования порядка между источниками.
- Отмену при ожидании чтения и при ожидании отправки, закрытие выхода и сохранение владения входами.

Обычные ожидания ограничены сторожевым таймером в две секунды. Тест таймаута проверяет исход, а не точную скорость. Для успешного пути используется заведомо длинный внутренний таймер, но внешний watchdog всё равно ограничивает проверку.

Для отмены блокирующей отправки используется стандартный `testing/synctest`: он позволяет дождаться устойчивой блокировки фоновой горутины без `Sleep`. Затем тест отменяет работу и проверяет, что выход закрылся **до получения ожидавшего значения**. Это важно: обычное чтение выхода могло бы случайно освободить отправителя и скрыть отсутствие обработки отмены.

`synctest` — часть тестовой инфраструктуры; в рабочем примере её нет. Общий `-timeout 10s` дополнительно ограничивает весь запуск пакета. Внешних зависимостей не добавлено.

### 3. Вывод кода

Какая тройка результатов получится у `receiveWithin(nil, 0)`?

<details>
<summary>Показать ответ и объяснение</summary>

`0, false, errTimeout`. Приём из nil-канала никогда не готов, а таймер с нулевой длительностью завершает ожидание. У закрытого пустого канала при успешном чтении ошибка была бы `nil`.

</details>

### 4. Типичная ошибка

Почему запись `case <-time.After(timeout)` внутри цикла не задаёт единый дедлайн на весь цикл?

<details>
<summary>Показать ответ и объяснение</summary>

На каждом входе в `select` создаётся новый таймер. Чтобы не перезапускать отсчёт, создай один таймер до цикла и выходи, когда выбрана его ветка. У неё нет приоритета: если одновременно готово и чтение данных, `select` может выбрать его.

</details>

### 5. Типичная ошибка

Почему в пересылке нужно проверять отмену и при отправке, если при чтении она уже проверяется?

<details>
<summary>Показать ответ и объяснение</summary>

Потребитель может перестать читать между получением значения и его отправкой. Если отправка стоит вне `select` с отменой, пересылающая горутина застрянет именно там.

</details>
