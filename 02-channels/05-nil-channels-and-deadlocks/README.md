# nil-каналы и deadlocks

## Цель

Научиться отличать nil-канал от закрытого, отключать ветки `select` и находить причины взаимных блокировок. Перед уроком нужны отправка, получение, закрытие каналов и `select`.

## Запуск из корня

```bash
go run -race ./02-channels/05-nil-channels-and-deadlocks
go test -count=1 -race -timeout 20s ./02-channels/05-nil-channels-and-deadlocks
```

`main` содержит восемь блоков и завершается самостоятельно. Опасные примеры ниже приведены только для чтения: основной запуск не вызывает panic, не зависает и не оставляет заблокированные горутины.

## 1. Три состояния канала

| Операция | nil | Открытый | Закрытый |
|---|---|---|---|
| Получение | Блокируется навсегда | Ждёт значение или отправителя | Читает остаток буфера, затем сразу возвращает zero value и `false` |
| Отправка | Блокируется навсегда | Ждёт получателя или свободное место | Panic |
| `close` | Panic | Закрывает канал | Panic |

Нулевое значение `chan T` — `nil`. Для создания рабочего канала нужен `make`. Для nil-канала `len` и `cap` равны нулю, но это не делает его рабочим небуферизированным каналом.

```go
var absent chan int          // nil
ready := make(chan int)      // рабочий небуферизированный канал
buffered := make(chan int, 2) // рабочий канал с буфером
```

`len` и `cap` не показывают, закрыт ли канал. Не пытайтесь проверять готовность конкурентной операции через `len`: состояние может измениться сразу после проверки.

## 2. nil отключает ветку select

Операция с nil-каналом никогда не готова, поэтому `select` её не выбирает. В `main` отправка и получение по nil-каналу соседствуют с `default`: программа выбирает `default`, не блокируясь.

Если `default` отсутствует и все канальные ветки используют nil, `select` блокируется навсегда. Пустой `select {}` также блокируется навсегда.

Это полезный инструмент: присваивание локальной переменной канала значения `nil` отключает соответствующую ветку. Оно не закрывает исходный канал и не меняет другие переменные, указывающие на него.

## 3. Закрытый канал нельзя оставлять активным бесконечно

После опустошения закрытый канал всегда готов к получению. Если не проверять `ok`, цикл может бесконечно обрабатывать нулевые значения и тратить CPU.

В `drainTwo` каждый вход читается до закрытия:

```go
case value, ok := <-first:
    if !ok {
        first = nil
        continue
    }
    results = append(results, value)
```

После закрытия обоих входов условие `first != nil || second != nil` становится ложным. Эта проверка важна: без неё следующий `select` с двумя nil-входами заблокируется навсегда.

Контракт функции:

- nil-вход считается отключённым;
- значения, включая нули и повторы, сохраняются;
- порядок внутри каждого входа сохраняется, общий порядок не определён;
- каждый ненулевой вход должен в итоге закрыться;
- отмены нет: если производитель перестал отправлять и не закрыл канал, функция продолжит ждать;
- функция накапливает результаты в памяти и предназначена для конечных потоков.

В реальной операции с независимым временем жизни добавьте `context.Context` и ветку отмены. Здесь оставлен минимальный пример именно отключения веток.

## 4. Deadlock: никто не может продолжить

Небуферизированная отправка требует получателя. Такой код не дойдёт до чтения:

```go
ch := make(chan int)
ch <- 1 // некому принять; текущая горутина заблокирована
fmt.Println(<-ch)
```

В `main` отправитель работает в отдельной горутине, а основная горутина принимает значение. Отдельный сигнал завершения позволяет дождаться выхода отправителя.

Другой частый случай — цикл по каналу, который никто не закроет:

```go
for value := range ch {
    fmt.Println(value)
}
// Если отправители ушли без close, цикл не узнает о конце потока.
```

И ещё один — неверный порядок ожидания:

```go
// Работник должен отправить значение и только потом вызвать Done.
wg.Wait() // main ждёт Done, работник ждёт получателя
value := <-ch
```

Нужно организовать чтение до ожидания либо вынести координацию завершения и закрытие канала в отдельную горутину. Закрывает канал тот, кто знает, что отправок больше не будет; получатель не должен закрывать его только ради разблокировки отправителя.

## 5. Буфер не исправляет протокол

Буфер позволяет завершить несколько отправок без получателя. После заполнения следующая отправка блокируется. Увеличение буфера может только отложить проблему.

В `main` заполненный канал проверяется через `select` с `default`, затем основная горутина освобождает место и отправляет следующее значение. Здесь `default` нужен для демонстрации неблокирующей попытки, а не для busy loop.

## 6. Deadlock, утечка и гонка — разные проблемы

- **Deadlock:** участники не могут продолжить из-за ожидания событий, которые не произойдут.
- **Утечка горутины:** часть программы продолжает работать, но отдельная горутина навсегда остаётся заблокированной.
- **Гонка данных:** конкурентные обращения к общей памяти без необходимой синхронизации, хотя бы одно из которых — запись.

Runtime может сообщить `fatal error: all goroutines are asleep - deadlock!`, когда обнаруживает глобальную блокировку. Но отсутствие такого сообщения не доказывает корректность: в программе может остаться активная горутина, таймер или внешнее ожидание, а другая часть уже зависла.

`-race` ищет гонки данных, но не является детектором deadlocks. Ограничение `go test -timeout 20s` помогает остановить зависшие тесты и получить стеки горутин. `time.Sleep` не исправляет ошибочный порядок взаимодействия.

## Разбор кода без запуска

Считай каждый фрагмент отдельным телом `main` с импортом `fmt`. Определи, что он напечатает и завершится ли нормально. Зависания и панику запускать не нужно.

### 1. Найди ошибку: последний вход отключён

```go
ch := make(chan int, 1)
ch <- 7
close(ch)
for {
    select {
    case v, ok := <-ch:
        if !ok {
            ch = nil
            continue
        }
        fmt.Println(v)
    }
}
```

<details>
<summary>Показать ответ и объяснение</summary>

Сначала напечатается `7`. Следующее чтение вернёт `0, false`, и `ch` станет `nil`. На следующей итерации ни одна ветка не готова и `select` заблокируется навсегда. Для одного входа здесь достаточно `return` при `!ok` или `for v := range ch`. Для нескольких входов выходи, как только отключены все.

</details>

### 2. Что выведет: `default` и закрытый канал

```go
ch := make(chan int, 1)
close(ch)
select {
case ch <- 7:
    fmt.Println("sent")
default:
    fmt.Println("not sent")
}
```

<details>
<summary>Показать ответ и объяснение</summary>

Ни одна строка из фрагмента не напечатается: отправка в закрытый канал вызывает панику. `default` срабатывает, когда нет готовых канальных операций, а не перехватывает панику. Нужен протокол, при котором закрытие происходит только после окончания всех отправок.

</details>
