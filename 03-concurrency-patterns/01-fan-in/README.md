# Fan-in: объединение каналов

## Что изучаем

Fan-in объединяет несколько входных каналов в один выходной. Потребителю не нужно отдельно читать каждый источник. Перед этим уроком нужно знать отправку и получение значений, `range` по каналу, закрытие каналов и `sync.WaitGroup`.

## Как запустить

Из корня репозитория:

```bash
go run ./03-concurrency-patterns/01-fan-in
go test -race -timeout 10s ./03-concurrency-patterns/01-fan-in
```

Пример выводит числа от 1 до 6, каждое ровно один раз. Общий порядок не гарантирован: например, `2` может появиться раньше `1`. При этом порядок значений каждого отдельного источника сохраняется: `1, 3, 5` и `2, 4, 6`.

## Как это работает

1. `fanIn(channels ...<-chan int)` принимает любое число каналов только для чтения и сразу возвращает выходной канал.
2. Для каждого входа запускается горутина. Она читает значения через `range` и пересылает их в общий `out`.
3. До запуска горутин `WaitGroup` получает число входов. Каждая пересылающая горутина вызывает `Done`, когда её вход закрыт и все значения переданы.
4. Отдельная горутина ждёт `wg.Wait()` и закрывает `out`. Потребитель завершает свой `range`, когда выход закрыт и прочитан.

Производители закрывают свои входы. Выход закрывает только координатор внутри `fanIn`: если отдельный пересылающий обработчик закроет его раньше остальных, следующая отправка вызовет панику. Потребитель получает канал только для чтения и закрывать его не должен.

При вызове без входов счётчик равен нулю: выход закроется без значений. Заранее закрытые входы тоже допустимы, включая каналы с оставшимися в буфере значениями.

## Ограничения

- Каждый вход должен в итоге закрыться. Незакрытый вход удерживает свою пересылающую горутину и не позволяет закрыть выход.
- `nil`-канал не равен закрытому каналу: чтение из него блокируется навсегда. Эта версия не пропускает `nil`-входы.
- Потребитель должен дочитать выход. Если он уйдёт раньше, отправки в `out` могут заблокироваться, а горутины останутся ждать.
- Отмена и таймауты внутри `fanIn` не реализованы. Для досрочного завершения потребуется, например, `context.Context` и `select` как при чтении, так и при отправке; производители также должны поддерживать отмену.
- Выход небуферизированный: медленный потребитель замедляет пересылку и затем производителей. Буфер может сгладить краткие задержки, но не решает проблему досрочного прекращения чтения.
- Создаётся по одной горутине на вход и ещё одна для закрытия выхода. При большом числе источников это нужно учитывать.

## Что проверяют тесты

Проверяются состав результата с учётом повторов, отсутствие входов, пустые входы, один и несколько источников, небуферизированные каналы и порядок одного источника. Сбор результата ограничен одним таймером в две секунды, включая ожидание закрытия выхода. Флаг `-timeout 10s` дополнительно ограничивает весь запуск пакета.

Таймер теста обнаруживает зависание, но не добавляет отмену в сам алгоритм. Входы `nil` и досрочный уход потребителя описаны как ограничения: тесты не оставляют намеренно заблокированные горутины для их демонстрации.

## Попробуй самостоятельно

1. Добавь третий источник и проверь, что каждое значение попало в результат ровно один раз.
2. Объясни, почему нельзя проверять общий результат сравнением с упорядоченным списком без сортировки.
3. Добавь буфер выходу. Какие задержки он сглаживает и чего не гарантирует?
4. Спроектируй версию с отменой: какие операции должны использовать `select`?
