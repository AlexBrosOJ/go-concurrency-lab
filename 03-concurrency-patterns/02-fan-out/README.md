# Fan-out: распределение работы

## Что изучаем

Fan-out позволяет нескольким обработчикам читать задачи из одного канала. В этом примере каждый обработчик вычисляет квадрат полученного числа, а результаты собираются в общий канал. Это простая основа пула воркеров: число обработчиков фиксировано, отдельная горутина на каждую задачу не создаётся.

Перед уроком нужно понимать каналы, `range`, `sync.WaitGroup` и [fan-in](../01-fan-in/README.md).

## Как запустить

Из корня репозитория:

```bash
go run ./03-concurrency-patterns/02-fan-out
go test -race -timeout 10s ./03-concurrency-patterns/02-fan-out
```

Программа запускает три обработчика и передаёт числа `1, 2, 3, 4, 5, 6`. В выводе будут `1, 4, 9, 16, 25, 36`, каждое один раз, в произвольном порядке.

## Как это работает

1. Производитель отправляет числа в `jobs` и закрывает его после последней задачи.
2. `fanOut(in, workers)` проверяет положительное число обработчиков, создаёт выход и запускает `workers` горутин.
3. Все обработчики читают один и тот же `in`. Каждое отправленное значение получает один из них: это распределение задач, а не рассылка копии каждому обработчику.
4. Получатель вычисляет `value * value` и отправляет результат в `out`. Общий канал результатов выполняет роль объединения выходов обработчиков.
5. Когда вход закрыт и прочитан, обработчики завершают циклы и вызывают `Done`. Координатор ждёт всех и закрывает выход.
6. `main` читает выход до закрытия; завершение `range` означает, что все результаты получены.

Вызывающий код владеет входом и закрывает его. Обработчики вход не закрывают. Выход закрывает единственная координирующая горутина после `Wait`, чтобы не прервать отправки остальных.

Функция сразу возвращает канал, а обработка продолжается в фоне. При пустом закрытом входе выход закроется без значений. Если обработчиков больше, чем задач, часть из них может не получить ни одной задачи.

## Ограничения

- Распределение не обязано быть равномерным: планировщик не гарантирует, что каждый обработчик получит задачу.
- Порядок результатов не гарантирован при нескольких обработчиках. Для восстановления порядка можно передавать вместе с задачей её индекс.
- `workers <= 0` вызывает панику до запуска горутин: здесь это ошибка использования функции. В библиотечном API можно выбрать возврат ошибки.
- `nil`-вход или вход, который никогда не закрывается, не позволяет завершить обработчики и закрыть выход.
- Выход нужно дочитать. Отмена не реализована: если потребитель уйдёт раньше, обработчики могут остаться заблокированными на отправке. Добавление буфера не заменяет отмену.
- Фиксированное число горутин ограничивает число одновременно обрабатываемых задач, но не частоту запросов в секунду. Это не rate limiter.
- Вычисления используют `int` без проверки переполнения. Для экспериментов выбирай небольшие числа.
- Пример с квадратами показывает механику распределения. Для столь короткой операции затраты на каналы могут превышать выигрыш от параллельности.

## Что проверяют тесты

Тесты проверяют пустой вход, одного и нескольких обработчиков, избыток обработчиков относительно задач, повторы, ноль и отрицательные числа, а также отклонение неположительного числа обработчиков. Для проверки передачи используются небуферизированные входы.

Результаты сравниваются после сортировки, с учётом количества повторов. Тесты не требуют равномерного распределения задач или конкретного порядка вывода. Один таймер ограничивает сбор результата и ожидание закрытия двумя секундами; `-timeout 10s` ограничивает весь запуск пакета. Таймер теста не является механизмом отмены обработчиков.

## Попробуй самостоятельно

1. Измени число обработчиков на один, затем на пять. Какие свойства результата сохраняются?
2. Передавай задачи с индексами и восстанови исходный порядок результатов.
3. Замени возведение в квадрат более длительной операцией и сравни время работы с одним и несколькими обработчиками.
4. Спроектируй отмену для производителя и обработчиков. Как завершить отправку, если потребитель перестал читать?
