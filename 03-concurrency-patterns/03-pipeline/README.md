# Pipeline: конвейер обработки данных

## Цель

Научиться соединять несколько стадий обработки каналами так, чтобы каждая стадия отвечала за одну операцию, потоки корректно закрывались, а досрочный уход потребителя не оставлял заблокированные горутины.

В этом уроке строим конвейер:

```text
[]int → generate → square → onlyEven → потребитель
         источник   квадрат   фильтр
```

Для входа `[1, 2, 3, 4, 5, 6]` результатом будет `[4, 16, 36]`.

До этого урока пройди [закрытие каналов](../../02-channels/03-close-and-range/README.md), [select и таймауты](../../02-channels/04-select-and-timeouts/README.md), [nil-каналы и deadlocks](../../02-channels/05-nil-channels-and-deadlocks/README.md), [WaitGroup](../../01-goroutines/03-waitgroup/README.md). Полезно сравнить пример с [fan-out](../02-fan-out/README.md).

Здесь впервые используем `context` для управления всем конвейером. Это небольшое введение; подробная работа с контекстом и graceful shutdown останется в разделе 04.

## Как запустить

Из корня репозитория:

```bash
go run ./03-concurrency-patterns/03-pipeline
go test -v -timeout 10s ./03-concurrency-patterns/03-pipeline
go test -race -timeout 10s ./03-concurrency-patterns/03-pipeline
```

В `main.go` восемь демонстраций, каждая в отдельной функции. `Sleep` не используется. Последний пример намеренно ждёт дедлайн примерно 10 миллисекунд; фактическое время может оказаться больше из-за планирования.

Перед запуском предскажи результат для `[-4, 1, 2, 0, -2]` и объясни, кто должен остановить источник, если потребителю нужен только первый результат.

## 1. Что является стадией

Стадия получает значения, выполняет одну операцию и передаёт результат следующему участнику.

| Стадия | Вход | Выход | Соотношение значений |
|---|---|---|---|
| `generate` | Слайс чисел | Канал чисел | По одному значению на элемент |
| `square` | Канал чисел | Канал квадратов | Один вход → один выход |
| `onlyEven` | Канал чисел | Канал чётных чисел | Один вход → ноль или один выход |
| Потребитель | Конечный канал | Печать или накопление | Дочитывает поток либо отменяет работу |

Каждая из трёх стадий работает в своей горутине. Функция создания стадии запускает её и сразу возвращает выходной канал: она не ждёт обработки всего потока.

Канал имеет направление `<-chan int` в возвращаемом типе. Вызывающий код может читать результаты, но не отправлять в выход и не закрывать его.

## 2. Источник generate

`generate` принимает слайс, создаёт небуферизированный канал и отправляет числа последовательно. После последнего числа закрывает выход.

```go
select {
case out <- number:
case <-ctx.Done():
    return
}
```

Это обычная отправка с дополнительным способом выйти из ожидания. Если следующая стадия перестала читать, источник может завершиться по отмене.

Перед очередной отправкой есть проверка `ctx.Err()`. Для заранее отменённого контекста источник не начнёт выдачу данных. Но эта проверка не создаёт строгого приоритета отмены при состязании: отмена может произойти сразу после неё, одновременно с готовой отправкой.

Слайс читается без копирования. Не меняй его элементы, пока источник работает. Если нужна независимость, создай копию до передачи; сам канал не синхронизирует доступ к исходному слайсу со стороны вызывающего кода.

Пустой или `nil`-слайс означает пустой поток: выход закроется без значений.

## 3. Преобразование square

Стадия получает число и вычисляет `number * number`.

Ожидание входа включает проверку закрытия:

```go
select {
case <-ctx.Done():
    return
case value, ok := <-in:
    if !ok {
        return
    }
    number = value
}
```

Полученное `0` — обычные данные. Конец потока определяется только `ok == false`.

После вычисления выполняется **другой** `select` — отправка результата или отмена. Добавить отмену только к получению недостаточно: стадия могла уже принять число и заблокироваться на следующей отправке.

Выход закрывается через `defer close(out)` при нормальном завершении и при отмене. Вход принадлежит предыдущей стадии и никогда не закрывается получателем.

Используется `int` без проверки переполнения. Большие числа могут дать математически неверный квадрат из-за переполнения; для этого урока выбирай небольшие значения.

## 4. Фильтр onlyEven

Фильтр читает поток тем же способом, но передаёт дальше только значения, у которых `number % 2 == 0`.

```go
if number%2 != 0 {
    continue
}
```

Поэтому длина выхода может быть меньше длины входа. Для нечётных входных чисел их квадраты тоже нечётны и будут отброшены. Ноль проходит фильтр.

Если не подошло ни одно число, выход всё равно нужно закрыть. Иначе потребитель не сможет отличить пустой законченный поток от временного отсутствия данных.

Не считай пустой результат ошибкой автоматически: в примере `[1, 3, 5]` корректно даёт ноль результатов.

## 5. Сборка pipeline и ожидание всех стадий

```go
source := generate(ctx, &wg, numbers)
squared := square(ctx, &wg, source)
values := onlyEven(ctx, &wg, squared)
```

Каждая стадия регистрируется через `wg.Add(1)` **до запуска своей горутины**. Стадии построены до запуска координатора с `wg.Wait()`. В этом уроке нельзя добавлять новые стадии в ту же группу после начала ожидания завершения.

`pipeline` возвращает два канала:

```go
values, finished := pipeline(ctx, numbers)
```

- `values` передаёт конечные результаты.
- `finished` закрывается после выхода всех трёх стадий, включая источник.

Завершение чтения конечного канала говорит о закрытии выхода последней стадии. Само по себе оно не является универсальным доказательством выхода всех остальных горутин, особенно при отмене. Поэтому жизненный цикл проверяется отдельно через `<-finished`.

Каждая стадия сначала закрывает свой выход, затем вызывает `wg.Done()` благодаря обратному порядку отложенных вызовов. Координатор закрывает `finished`, когда все задачи группы завершены.

У `WaitGroup` и `context` разные обязанности: первая ждёт, второй даёт участникам сигнал остановиться. `WaitGroup` сам по себе не отменяет горутины.

## 6. Как распространяется нормальное завершение

Без отмены поток заканчивается слева направо:

1. Источник отправил последнее число и закрыл свой канал.
2. `square` получил все числа, обнаружил конец входа и закрыл свой выход.
3. `onlyEven` обработал все квадраты, обнаружил конец и закрыл конечный канал.
4. Потребитель закончил `range`.
5. Получение из `finished` подтверждает выход всех стадий.

Не нужно передавать специальное число-маркер, например `-1`: оно могло бы оказаться законными входными данными. Сигналом конца служит закрытие.

## 7. Порядок и обратное давление

Все каналы небуферизированные. Если потребитель медленный, `onlyEven` ждёт передачи результата; затем `square` может ждать фильтр, а источник — преобразователь. Это обратное давление: задержка downstream ограничивает продвижение upstream.

При этом элементы, отбрасываемые фильтром, не требуют отправки конечному потребителю. Нельзя по размеру одного канала или числу результатов точно судить о числе уже обработанных входов.

Конвейер не хранит неограниченную очередь между стадиями. Однако входной слайс остаётся в памяти, а у каждой стадии может быть уже принятое значение или готовый результат. Небуферизированные каналы не означают нулевое потребление памяти.

Одна горутина на стадию сохраняет относительный порядок проходящих значений. Для входа `[-4, 1, 2, 0, -2]` выход будет именно `[16, 4, 0, 4]`, без сортировки.

Если позже заменить стадию несколькими воркерами, порядок завершения задач может измениться. Для восстановления порядка тогда понадобятся индексы или отдельный протокол.

## 8. Повторное использование стадии

В `reusableStageExample` одна и та же функция `square` вызывается дважды:

```text
[1, 2, 3] → generate → square → square → [1, 16, 81]
```

Это **две разные горутины** и два разных выходных канала, созданные одним кодом. Стадия не зависит от того, кто произвёл входные числа: источник, другая стадия или внешний компонент.

В примере сборка выполняется вручную, а после чтения вызывается `wg.Wait()`. Такой вариант подходит для эксперимента с порядком стадий. Готовая функция `pipeline` фиксирует конкретную цепочку из трёх стадий.

## 9. Ранний выход потребителя

Неправильный протокол:

```go
for value := range values {
    fmt.Println(value)
    break
}
// Остальные участники не получили сигнала об остановке.
```

`break` завершает только цикл. Последняя стадия может остаться ждать отправки следующего результата, предыдущие — ждать друг друга.

В `earlyExitExample` используется дочерний контекст:

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()
values, finished := pipeline(ctx, numbers)

if value, ok := <-values; ok {
    fmt.Println(value)
}
cancel()
<-finished
```

Потребитель забирает первый результат, отменяет работу и ждёт выхода всех стадий, **не дочитывая конечный канал**. Именно это проверяет, что отмена действительно освобождает блокирующие отправки.

Повторный вызов `cancel` допустим: явный вызов останавливает работу сейчас, отложенный гарантирует уборку при других путях выхода.

## 10. Если потребитель вообще не начал чтение

В `unreadOutputExample` создаётся конвейер, но его результаты не читаются. После `cancel()` программа ждёт `finished`.

Некоторые стадии могли ещё не запуститься, другие — уже дойти до блокировки. Правильность не должна зависеть от этого. В тесте с `testing/synctest` мы дополнительно дожидаемся устойчивой блокировки стадий и только потом отменяем работу.

Если тест сначала начнёт читать выход для «помощи» завершению, он может скрыть дефект отмены. Поэтому тест ждёт завершения всех стадий до любого последующего чтения.

## 11. Дедлайн при пустом входе

В `deadlineExample` стадия `square` получает `nil`-вход. Операция чтения никогда не готова, но контекст имеет дедлайн:

```go
ctx, cancel := context.WithTimeout(context.Background(), 10*time.Millisecond)
defer cancel()
out := square(ctx, &wg, nil)
```

По истечении срока `ctx.Done()` становится готов к чтению, стадия выходит и закрывает выход. `ctx.Err()` возвращает `context.DeadlineExceeded`.

`context.WithCancel` сообщает об обычной отмене через `context.Canceled`. При нормальном завершении без отмены `ctx.Err()` равен `nil`.

Контекст — кооперативный сигнал, а не принудительное прерывание. Он не остановит произвольное долгое вычисление внутри `number * number` или внешней функции; обработка должна сама проверять отмену либо вызывать API, которое её поддерживает.

Не передавай `nil` вместо контекста. Для работы без отмены используй `context.Background()`: его `Done()` равен `nil`, и соответствующая ветка `select` отключена.

## Pipeline, fan-in и fan-out

| Паттерн | Что меняется |
|---|---|
| Pipeline | Данные последовательно проходят разные операции |
| Fan-out | Несколько обработчиков делят задачи одной операции |
| Fan-in | Несколько потоков результатов объединяются в один |

Паттерны можно сочетать: внутри одной стадии запустить несколько воркеров, затем объединить их результаты и передать следующей стадии. В таком варианте придётся заново определить порядок результатов и владельца закрытия общего выхода.

## Ограничения и типичные ошибки

- **Забыть отмену у источника.** Остановить только последнюю стадию недостаточно: источник тоже может ждать отправки.
- **Проверять отмену только при чтении.** Отправка дальше также блокируется и должна учитывать `ctx.Done()`.
- **Закрыть чужой вход из потребителя.** Производитель может в этот момент отправлять; получится паника. Используй сигнал отмены и дай владельцу закрыть выход.
- **Ждать до отмены при раннем выходе.** Если никто не читает результаты, `Wait` может ждать навсегда. Сначала отмени, потом дождись.
- **Гарантировать строгую границу после cancel.** Если отправка и отмена одновременно готовы, `select` может выбрать отправку. Контекст не обеспечивает приоритета отмены над данными; после подтверждённого `finished` все стадии уже вышли.
- **Потерять причину завершения.** Конечный канал закрывается и при нормальном завершении, и при отмене. Для причины смотри `ctx.Err()`; ошибки обработки в данном примере отдельно не передаются.
- **Считать конвейер ускорением любой задачи.** Для возведения маленьких чисел в квадрат затраты каналов могут быть больше вычислений. Пример показывает протокол, а не обещает выигрыш производительности.
- **Бесконечно накапливать результаты.** Потоковая передача не спасает память, если потребитель всё сохраняет в растущий слайс.

## Что проверяют тесты

1. Пустой и `nil`-вход, отсутствие подходящих значений, один результат и настоящий ноль.
2. Отрицательные числа, повторы и точный порядок выходов без сортировки.
3. Повторное применение стадии: четвёртая степень чисел.
4. Нормальное закрытие конечного потока и завершение всех стадий.
5. Остановку после первого результата без дочитывания выхода.
6. Заранее отменённый контекст.
7. Отмену при полностью непрочитанном выходе и заблокированных стадиях.
8. Отмену чтения `nil`-входа отдельно у преобразования и фильтра.
9. Дедлайн у стадии, которая ждёт данные.

Сбор результатов ограничен одним таймером в две секунды, включая ожидание закрытия. Ожидание `finished` тоже ограничено. Cleanup отменяет конвейер и дожидается стадий даже после раннего падения теста.

Для устойчивой блокировки используется стандартный `testing/synctest`, поэтому тесты не угадывают скорость планировщика через `Sleep`. Внутри такой проверки время виртуальное; тест дедлайна не обязан ждать реальную секунду. Глобальный `-timeout 10s` дополнительно ограничивает весь пакет.

Таймаут проверки не способен принудительно убить дефектную горутину. Если код перестанет учитывать отмену, проверка должна завершиться ошибкой, а не считать исчезновение результатов успешным завершением.

4. Поставь буфер между стадиями. Какие гарантии сохраняются и что меняется в объёме накопленных данных?
5. Убери обработку отмены из одной отправки и запусти тест с непрочитанным выходом. Почему обычный тест полного чтения мог бы не заметить дефект?
6. Передай структуру с идентификатором задачи. Как сохранить связь результата с исходным элементом?
7. Спроектируй передачу ошибки обработки. Кто отменяет остальные стадии после первой ошибки и кто закрывает канал ошибок?
8. Замени одну стадию несколькими воркерами. Какие тесты порядка придётся пересмотреть?
9. Объясни, почему контекст лучше передавать всем стадиям явно и почему отмена без ожидания ещё не означает законченной уборки.

</details>

### 4. Типичная ошибка

Где может остановиться конвейер, если потребитель прочитал первый результат и ждёт `finished` без отмены?

<details>
<summary>Показать ответ и объяснение</summary>

Последняя стадия может ждать чтения следующего результата, предыдущие стадии могут ждать её. Сначала вызови `cancel()`, затем жди `finished`. Все блокирующие операции стадий должны учитывать этот сигнал.

</details>

### 5. Типичная ошибка

Почему нельзя менять элементы исходного слайса сразу после вызова `pipeline`?

<details>
<summary>Показать ответ и объяснение</summary>

Источник читает переданный слайс из фоновой горутины без копии массива. Одновременная запись может создать гонку. Передай отдельную копию либо дождись `finished` перед изменениями.

</details>
