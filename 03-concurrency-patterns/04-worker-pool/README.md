# Worker Pool — пул обработчиков

## Цель

Научиться обрабатывать список задач с заданным пределом конкурентности. Разберём, как отличаются размер очереди и число обработчиков, кто закрывает каналы, как связать результат с задачей и что происходит с очередью при отмене.

Пул продолжает идею [fan-out](../02-fan-out/README.md). Теперь у задачи есть идентификатор, обработчик может вернуть ошибку, очередь имеет настраиваемую ёмкость, а производитель и обработчики получают общий сигнал отмены. Правила закрытия и отмены знакомы по уроку о конвейере. [Pipeline](../03-pipeline/README.md)

## Запуск

Из корня репозитория:

```bash
go run ./03-concurrency-patterns/04-worker-pool
go test -v -timeout 10s ./03-concurrency-patterns/04-worker-pool
go test -race -timeout 10s ./03-concurrency-patterns/04-worker-pool
```

В программе пять сценариев. Перед запуском предскажи, сколько результатов будет у второй партии из четырёх задач, если текст одной задачи состоит только из пробелов.

## 1. Задача, обработчик и результат

```go
type Job struct {
    ID   int
    Text string
}

type Result struct {
    ID    int
    Words int
    Err   error
}
```

Обработчик получает задачу и возвращает число слов либо ошибку. `strings.Fields` выделяет непустые фрагменты между пробельными символами, включая пробелы Unicode. Для пустого текста и текста из одних пробелов в этом уроке возвращается ошибка. Пунктуация внутри фрагмента остаётся его частью.

Пул копирует `Job.ID` в `Result.ID`. Так вызывающий код может сопоставить результаты с исходными задачами, даже когда разные обработчики заканчивают в разном порядке. Если вызывающему коду нужно однозначное сопоставление, он сам назначает уникальные идентификаторы. Пул обрабатывает каждую запись партии и допускает повторяющиеся ID.

Одна ошибка обработки даёт один результат с `Err` и не отменяет остальную партию. В обычном запуске с читаемым выходом каждая задача возвращает один результат, включая задачи с ошибками. При отмене часть задач может остаться в очереди, а результат уже начатой задачи может не дойти до потребителя.

## 2. Из чего состоит пул

```mermaid
flowchart LR
    P["Производитель партии"] --> Q["Канал jobs"]
    Q --> W1["Обработчик 1"]
    Q --> W2["Обработчик 2"]
    W1 --> O["Канал out"]
    W2 --> O
    O --> C["Потребитель"]
```

Вызов `startPool(ctx, batch, 2, 3, countWords)` запускает одного производителя, двух обработчиков и одного координатора. Производитель отправляет задачи из слайса в общий канал. Каждую задачу получает один обработчик. Он вызывает функцию обработки и отправляет результат в общий выход. Координатор ждёт завершения производителя и обработчиков через `WaitGroup`, затем закрывает выход.

Обработчики создаются один раз на партию и берут задачи в цикле. При двух обработчиках одновременно может выполняться до двух вызовов `process`. Эта граница относится именно к вызовам функции. Если она сама запускает фоновые горутины и возвращается до их завершения, пул ими не управляет.

## 3. Обработчики и ёмкость очереди

| Настройка | За что отвечает |
|---|---|
| `workers` | Сколько обработчиков читают одну очередь и сколько вызовов `process` может идти одновременно |
| `queueSize` | Сколько ещё не полученных задач помещается в канале `jobs` |
| Небуферизированный `out` | Обработчик ждёт потребителя при передаче готового результата |

При двух занятых обработчиках и очереди ёмкостью три в очереди могут ждать ещё три задачи. Если очередь полна, производитель ждёт, пока один из обработчиков освободит место. Если потребитель медленно читает результаты, обработчики могут остановиться на отправке в `out`. Тогда очередь перестаёт освобождаться и обратное давление доходит до производителя.

При `queueSize == 0` производитель передаёт задачу напрямую готовому обработчику. При положительной ёмкости он может немного опередить обработчиков. Исходный слайс партии уже находится в памяти, поэтому настройка очереди ограничивает только число задач в канале, а не размер всей партии.

Два обработчика не гарантируют одинакового числа задач у каждого. Фиксированный пул ограничивает число одновременно выполняемых вызовов и не задаёт число задач в секунду.

## 4. Кто закрывает канал

| Канал | Кто закрывает | Когда |
|---|---|---|
| `jobs` | Производитель | Когда отправил партию или завершился по отмене |
| `out` | Координатор | После выхода производителя и всех обработчиков |

Производитель единолично владеет закрытием `jobs`. Обработчик обнаруживает конец очереди через `job, ok := <-jobs`. При нормальном завершении закрытие буферизированного канала сохраняет стоящие в очереди задачи, поэтому обработчики продолжают принимать их до опустошения.

Канал `out` общий для всех отправителей. Если первый закончивший обработчик закроет его сам, другой обработчик может попытаться отправить результат в закрытый канал и вызвать панику. Координатор ждёт всех участников через `WaitGroup` и закрывает выход один раз. Все задачи группы зарегистрированы до запуска ожидания.

Когда `range out` заканчивается, производитель и обработчики уже завершились. Пустая партия проходит тот же протокол и закрывает выход без результатов.

## 5. Порядок и ошибки

В сценарии с двумя обработчиками задача с ID 3 может завершиться после задачи с ID 1, хотя производитель отправляет её раньше. Порядок поступления результатов не закреплён. Программа собирает результаты и сортирует их по ID перед печатью, поэтому вывод воспроизводим. При потоковой обработке большие партии обычно обрабатывают по мере поступления результатов, чтобы избежать хранения всех результатов в памяти.

Вторая партия содержит четыре задачи. Три дают число слов, четвёртая возвращает `empty text`. Это четыре результата. Ошибка обработки находится в `Result.Err`. Ошибка конфигурации возвращается сразу из `startPool`, до запуска горутин. Число обработчиков должно быть положительным, ёмкость очереди может быть нулевой или положительной.

## 6. Ранний выход и отмена

В четвёртом примере потребитель берёт первый результат и вызывает `cancel()`. Затем он читает канал до закрытия, игнорируя оставшиеся результаты.

```go
cancel()
for range out {
    // Ожидаем завершения пула и игнорируем поздние результаты.
}
```

Для корректной отмены учитываем все точки ожидания:

1. Производитель может ждать свободное место или готового обработчика при отправке в `jobs`.
2. Пустой обработчик может ждать следующую задачу.
3. Работающий обработчик может ждать потребителя при отправке в `out`.
4. Если сама обработка ждёт внешний ресурс, она должна реагировать на переданный `context` или использовать API с поддержкой контекста.

Во всех операциях с каналами пул выбирает между основной операцией и `ctx.Done()`. После чтения задачи он также проверяет `ctx.Err()`, чтобы не запускать её обработку, если отмена уже видна. Между проверкой и вызовом обработчика контекст всё равно может отмениться. Готовая отправка результата тоже может состязаться с отменой, поэтому потребитель допускает поздний результат. Обработчик, игнорирующий сигнал и блокирующийся навсегда, задержит закрытие `out`.

Если потребитель просто выйдет из цикла без отмены, обработчик может остаться ждать отправки результата, а производитель — освобождения очереди. Отмена прекращает обработку оставшейся партии по мере выхода участников. Для режима «перестать принимать новые задачи, но закончить все принятые» нужен отдельный протокол остановки приёма и дочитывания очереди.

Слайс партии читается в фоне. Вызывающий код может безопасно менять его элементы после закрытия выхода. До этого момента изменения требуют отдельной синхронизации.

## Ожидаемый вывод

```text
=== 1. One worker, no queue buffer ===
Job 1: 1 words
Job 2: 2 words
Job 3: 3 words
Pool finished: 3 results

=== 2. Two workers, buffered queue, one job error ===
Job 1: 1 words
Job 2: 2 words
Job 3: 3 words
Job 4: empty text
Pool finished: 4 results

=== 3. Empty batch ===
Pool finished: 0 results

=== 4. Consumer stops early ===
Kept job 1: 2 words
Pool stopped after cancellation

=== 5. Invalid configuration ===
workers must be positive and queue size nonnegative
```

## Как устроены тесты

- Полная партия проверяется по идентификаторам, числу слов и ошибке пустого текста. Сортировка ID позволяет обнаружить пропуски и дубликаты без ожидания конкретного порядка завершения.
- Пустая партия должна закрыть выход. Недопустимое число обработчиков или ёмкость очереди должны дать ошибку до запуска пула.
- Проверка предела конкурентности удерживает обработчики на явном барьере. Пока обработчики ждут освобождения барьера, должны стартовать ровно две задачи из шести. После освобождения барьера пул обязан вернуть все шесть результатов.
- Проверка отмены дожидается, пока производитель и обработчик заблокируются при непрочитанном выходе. Затем отменяет контекст и проверяет закрытие выхода, не освобождая отправку чтением.
- Отдельная проверка отменяет контекст во время обработки. Обработчик должен получить этот сигнал и завершиться, после чего закрывается выход.

Для ожиданий в тестах используются двухсекундные таймеры, а сбор всей партии ограничен одним общим таймером. `testing/synctest` позволяет дождаться устойчивой блокировки горутин без `time.Sleep`. Внутри этих тестов таймеры используют виртуальное время. Опция `-timeout 10s` ограничивает весь запуск пакета.

## Попробуй самостоятельно

1. Измени число обработчиков и ёмкость очереди независимо. Объясни, почему большой буфер при одном обработчике не позволяет обрабатывать две задачи сразу.
2. Убери сортировку из `printBatch`. Запусти пример несколько раз. Какие свойства вывода гарантированы даже при одинаковом порядке в нескольких запусках?
3. Добавь обработчик строк, который возвращает длину в рунах. Сможешь переиспользовать пул с той же сигнатурой?
4. Добавь явный порядковый номер записи. Собери результаты в исходном порядке партии, даже если у нескольких задач одинаковый ID.
5. Реализуй отмену партии после первой ошибки. Определи, какие уже полученные результаты сохраняются и почему после ошибки ещё может прийти результат.
6. Убери ветку отмены при отправке в `out` и запусти тест отмены без читателя. Объясни, почему тест полного чтения такой дефект пропустит.
7. Сравни буферизированную очередь задач и буферизированный выход результатов. Какой участник получает возможность продвинуться дальше в каждом случае?

## Самопроверка

Сначала ответь самостоятельно. Затем раскрой ответ и сравни объяснение со своим.

### 1. Понимание

При `workers == 2` и `queueSize == 3` сколько обработок могут выполняться одновременно и сколько задач ждут в самом буфере?

<details>
<summary>Показать ответ и объяснение</summary>

Одновременно выполняется до двух вызовов обработчика. Буфер может держать ещё до трёх задач, которых никто не забрал. Остальные задачи ещё остаются в исходной партии.

</details>

### 2. Вывод кода

Что напечатает `printBatch(2, 1, []Job{{ID: 2, Text: " "}, {ID: 1, Text: "два слова"}})`?

<details>
<summary>Показать ответ и объяснение</summary>

Строки `Job 1: 2 words`, `Job 2: empty text`, затем `Pool finished: 2 results`. У задачи с пробелами есть результат с ошибкой. Печать идёт по отсортированным ID.

</details>

### 3. Вывод кода

Что напечатает `printBatch(3, 0, nil)`?

<details>
<summary>Показать ответ и объяснение</summary>

`Pool finished: 0 results`. Производитель сразу закроет пустой вход, работники закончат ожидание, координатор закроет выход.

</details>

### 4. Типичная ошибка

Почему один закончивший работник не должен закрывать `out`?

<details>
<summary>Показать ответ и объяснение</summary>

Другой работник может ещё отправлять. Выход закрывает координатор после выхода всех участников, поэтому ни одна рабочая отправка не прерывается закрытием канала.

</details>

### 5. Типичная ошибка

Освободит ли отмена работника, который завис внутри `process` и не использует контекст?

<details>
<summary>Показать ответ и объяснение</summary>

Отмена разблокирует операции пула, которые следят за `ctx.Done()`. Она не прерывает произвольную функцию. Координатор будет ждать возврата обработчика, поэтому блокирующая работа должна реагировать на переданный контекст.

</details>
