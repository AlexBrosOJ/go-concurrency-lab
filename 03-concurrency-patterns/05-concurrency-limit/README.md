# Ограничение параллелизма

## Цель

Научиться выдавать разрешение на запуск задачи и возвращать его после работы. Соберём семафор на буферизированном канале, поставим ожидание разрешения под контроль контекста и проверим, что отмена останавливает новые запуски и позволяет дождаться уже начатых задач.

Предыдущий урок посвящён фиксированному числу обработчиков и очереди задач. [Worker Pool](../04-worker-pool/README.md)

## Запуск

Из корня репозитория выполни:

```bash
go run ./03-concurrency-patterns/05-concurrency-limit
go test -v -timeout 10s ./03-concurrency-patterns/05-concurrency-limit
go test -race -timeout 10s ./03-concurrency-patterns/05-concurrency-limit
```

Перед запуском предскажи, сколько задач успеет начать четвёртый пример при лимите 1. Посмотри, в какой момент первая задача вызывает `cancel()`.

## 1. Как канал становится семафором

```go
slots := make(semaphore, 2)
```

`semaphore` — тип на основе `chan struct{}`. Буфер на два элемента даёт два разрешения на работу. Отправка `slots <- struct{}{}` занимает место, чтение `<-slots` его освобождает. Пустая структура используется как отметка о занятости.

Семафор начинает работу с пустым буфером. После первого захвата в канале один элемент, после второго — два. Третья отправка ждёт, пока завершившаяся задача освободит место. Освобождать разрешение может горутина, которой передали работу, даже если захват выполнила запускающая горутина.

| Операция | Что происходит |
|---|---|
| Захват при свободном месте | Отправка занимает место в буфере |
| Захват при полном буфере | Вызывающая горутина ждёт освобождения места или отмены |
| Освобождение | Чтение из буфера возвращает одно место |

Это протокол учёта. На каждый успешный захват должно приходиться одно освобождение. Пропущенное освобождение постепенно исчерпает места. Лишнее чтение может украсть разрешение у другой задачи или заблокироваться на пустом канале. Семафор оставляют открытым, поскольку он используется повторно. Закрытие сделало бы следующий захват через отправку ошибкой с паникой.

Первый пример дважды использует одно и то же место. Вторая задача получает его после освобождения первой.

## 2. Захват до запуска горутины

`runLimited` идёт по списку и берёт разрешение перед каждым `go`. При полном семафоре сам цикл ждёт, а оставшиеся задачи остаются во входном слайсе.

```go
if err := slots.acquire(ctx); err != nil {
    break
}
wg.Add(1)
go func() {
    defer wg.Done()
    defer slots.release()
    process(ctx, input)
}()
```

После возврата из `process` отложенные вызовы выполняются в обратном порядке. Сначала возвращается место, затем `wg.Done()` отмечает завершение горутины. `wg.Wait()` вызывается после завершения цикла запуска, когда все регистрации уже сделаны.

Если создать горутину на каждый элемент и захватывать семафор уже внутри неё, предел вызовов `process` сохранится, но на большой партии можно накопить много горутин, ожидающих разрешения. Захват до `go` оставляет ожидание в одной запускающей горутине. В этой реализации точная гарантия относится к одновременным вызовам `process`. Завершающие инструкции горутины после освобождения семафора могут кратковременно пересекаться со стартом следующей.

Лимит 1 сериализует вызовы. Лимит больше 1 разрешает перекрытие по времени. Фактическое выполнение на нескольких ядрах зависит от характера работы, доступных ресурсов и планировщика. Лимит также не задаёт число операций в секунду.

## 3. Перекрытие работы и общие данные

Во втором примере до двух обработчиков вычисляют квадраты чисел одновременно. Затем каждый добавляет своё значение в общую сумму под `sync.Mutex`. Для чисел от 1 до 5 получается 55.

Выражение `total += squared` читает и меняет общее значение. Семафор ёмкостью 2 допускает одновременный доступ двух обработчиков, поэтому короткая критическая секция защищена отдельным мьютексом. Вычисление квадрата выполнено за пределами блокировки. Итог читается после возврата из `runLimited`, когда все запущенные операции уже завершились.

Порядок запуска через цикл и порядок фактического выполнения функций могут различаться. Сумма маленьких целых чисел от этого не меняется. Если требуется результат на каждый вход, можно сохранять его по уникальному индексу в заранее выделенном слайсе и читать слайс после ожидания всех задач. Сбор и представление результатов подробно разберём в следующем уроке.

## 4. Дедлайн и отмена захвата

Захват использует `select` между отправкой в семафор и сигналом `ctx.Done()`. Если место занято и истёк срок ожидания, вызов возвращает `context.DeadlineExceeded`. Разрешение, которым владела работающая задача, остаётся у неё.

`acquire` проверяет `ctx.Err()` до входа в `select` и сразу после успешной отправки. Когда освобождение места и отмена становятся готовы одновременно, `select` может выбрать отправку. Если повторная проверка уже видит отмену, функция возвращает только что захваченное место и передаёт ошибку вызывающему коду.

Отмена может прийти и после этой повторной проверки. Поэтому уже принятый к запуску обработчик получает тот же контекст и самостоятельно решает, как завершить работу. В примере с дедлайном единственное место удерживается до возврата из функции. Ветке отправки неоткуда получить свободное место, так что исход однозначен. Реальное ожидание может оказаться дольше заданных 10 мс.

## 5. Что значит отменить партию

В четвёртом сценарии лимит равен 1. Первая задача вызывает `cancel()`, пока ещё держит место. Цикл запуска получает сигнал остановки и прекращает выдавать разрешения. `runLimited` дожидается завершения уже запущенной задачи, после чего возвращает `context.Canceled`.

Семафор управляет допуском, а `WaitGroup` — ожиданием начатой работы. Контекст служит сигналом обоим участникам протокола. Если обработчик обращается к сети или диску, ему нужно передать контекст в API, которое умеет прервать ожидание, либо самому проверять сигнал между шагами. Если обработчик зависнет и проигнорирует контекст, вызов `runLimited` продолжит ожидать.

`runLimited` возвращает состояние контекста после ожидания. Контекст мог отмениться после выполнения последней задачи, поэтому возвращённая ошибка сама по себе не сообщает, сколько задач успели выполниться. Функция обработки в этом уроке не возвращает отдельную ошибку или результат. Вызывающий код может явно вести такой учёт, если он нужен.

Пятый сценарий показывает немедленный отказ при нулевом лимите. Отрицательный лимит также отклоняется до создания канала. Пустой список при действующем контексте и положительном лимите завершается успешно без вызовов обработчика.

## 6. Когда выбрать семафор или Worker Pool

| Вопрос | Семафор в этом уроке | Worker Pool из предыдущего урока |
|---|---|---|
| Кто ждёт, когда все заняты? | Цикл, который запускает задачи | Производитель, если очередь полна |
| Как устроены горутины? | Запускается отдельная горутина для каждой допущенной задачи | Фиксированные обработчики берут много задач за свою жизнь |
| Как передаётся работа? | Задача передаётся в вызов функции | Задача приходит через общий канал |
| Где удобно применять? | Группа вызовов к общему ограниченному ресурсу или конечная партия операций | Поток раздельных задач с очередью и повторно используемыми обработчиками |

Лимит выбирают по ресурсу, который нужно защитить. Для CPU важна доступная вычислительная мощность, для внешнего сервиса — сколько одновременных запросов он способен выдержать. Если нужен предел на несколько независимых вызовов одновременно, они должны разделять один семафор. Каждый вызов `runLimited` в этом уроке создаёт свой экземпляр, поэтому лимит действует в пределах партии.

## Ожидаемый вывод

```text
=== 1. Reuse a slot ===
First task acquired the only slot
Second task reused the slot

=== 2. Limit a batch ===
Sum of squares: 55; error: <nil>

=== 3. Deadline waiting for a slot ===
Waiting for the occupied slot: context deadline exceeded

=== 4. Cancel a batch ===
Started task: 1
Started 1 of 3; error: context canceled

=== 5. Reject an invalid limit ===
Configuration: limit must be positive
```

## Что проверяют тесты

1. При лимите 2, пока первые два обработчика удерживаются на барьере, остальные не стартуют. После освобождения каждая задача выполняется ровно один раз.
2. При отмене партия не запускает оставшиеся задачи и ждёт, пока активный обработчик закончит уборку.
3. Истечение срока ожидания не освобождает чужое место. После штатного освобождения слот можно снова занять.
4. Пустой список, нулевой и отрицательный лимиты, заранее отменённый контекст не запускают обработку.

`testing/synctest` позволяет проверить устойчивое ожидание на каналах и пройти дедлайн по виртуальному времени. Тестам не нужно угадывать длительность запуска горутины через `Sleep`. Ожидания результатов ограничены таймерами, а `-timeout 10s` ограничивает весь запуск пакета.

## Попробуй самостоятельно

1. Прогони второй пример с лимитами 1 и 5. Какие свойства результата и порядка сохраняются?
2. Добавь измерение числа активных обработчиков и максимума через атомарные операции. Сравни измерение с лимитом.
3. Перенеси захват в обёртку вызова внутри горутины и объясни, что произойдёт с числом ожидающих горутин на большой партии.
4. Добавь отдельный контекст для длительной задачи. Что произойдёт, если её дедлайн короче срока всей партии?
5. Спроектируй разделяемый семафор для двух независимых партий. Определи, кто создаёт его и как проверить общий предел.
6. Реализуй сбор результатов с исходными индексами и определись, как представить задачи, которые не стартовали после отмены.
