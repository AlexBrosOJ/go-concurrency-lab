# Сбор результатов параллельных операций

## Цель

Научиться принимать результаты по мере поступления, сопоставлять их с исходными задачами и отличать полезный ноль, ошибку задачи и отсутствие результата. На примерах разберём, что можно сохранить при отмене партии.

В предыдущих уроках мы ограничивали число активных задач и распределяли их между обработчиками. Здесь сосредоточимся на протоколе выдачи результатов. [Ограничение параллелизма](../05-concurrency-limit/README.md) · [Worker Pool](../04-worker-pool/README.md)

## Запуск

Из корня репозитория:

```bash
go run ./03-concurrency-patterns/06-collecting-results
go test -v -timeout 10s ./03-concurrency-patterns/06-collecting-results
go test -race -timeout 10s ./03-concurrency-patterns/06-collecting-results
```

Перед запуском посмотри на вход `[3, 0, -4, 3]`. Какие записи должны получиться, если обработчик удваивает неотрицательные числа и возвращает ошибку для отрицательных?

## 1. Результату нужна связь с задачей

`runTasks` запускает по горутине на элемент. Каждая горутина передаёт в общий канал структуру с исходным индексом, значением и ошибкой:

```go
type Result struct {
    Index int
    Value int
    Err   error
}
```

Одинаковые входные числа могут быть разными задачами. Входные тройки находятся на индексах 0 и 3. Обе дают значение 6, но остаются отдельными результатами. Если использовать значение входа как ключ, одну запись можно случайно затереть.

Учебный обработчик работает с маленькими целыми числами. Удвоение больших `int` потребовало бы отдельной проверки переполнения. Сам `runTasks` принимает функцию, чтобы протокол доставки можно было переиспользовать с другой обработкой.

## 2. Порядок поступления

Запуск задач в цикле задаёт порядок обхода входа. Планировщик и длительность работы определяют, кто первым сможет отправить результат. Даже порядок возврата из функций обработки не обязан совпасть с порядком отправок: горутину могут приостановить между этими действиями.

В первой демонстрации задача с индексом 0 ждёт сигнала. Задача с индексом 1 может отправить результат сразу. Потребитель получает его и только затем закрывает сигнальный канал. Так программа гарантированно показывает сначала индекс 1, потом 0. Задержка через `Sleep` не нужна.

Потоковый потребитель может печатать, записывать или анализировать каждую полученную запись сразу. Такой подход полезен, когда ранний результат уже приносит пользу, а общий порядок не важен.

## 3. Исходный порядок и частичный результат

`inInputOrder` заранее выделяет слайс длиной с партию и пишет результат в ячейку по индексу:

```go
entries[result.Index] = Entry{
    Value:    result.Value,
    Err:      result.Err,
    Received: true,
}
```

Запись создаёт одна горутина-потребитель. Другие горутины передают данные по каналу. Сортировка не нужна, потому что исходная позиция уже известна. Для составных внешних ID вместо индекса может понадобиться отображение ID в позицию.

| Состояние | Как его увидеть |
|---|---|
| Успешный ноль | `Received == true`, `Err == nil`, `Value == 0` |
| Ошибка обработчика | `Received == true`, `Err != nil` |
| Результат отсутствует | `Received == false` |

Отсутствие говорит только о доставке. Задача могла пропустить обработку при уже отменённом контексте, выйти из обработчика по отмене или закончить вычисление и пропустить отправку. Если нужно различить эти события, придётся явным образом записать состояния выполнения.

`inInputOrder` ожидает канал, созданный `runTasks`, с уникальными индексами в диапазоне от 0 до `size-1`. Для внешнего источника понадобятся проверки границ и повторов. Слайс занимает память пропорционально числу задач, даже при частичном результате.

## 4. Как закрывается выход

1. Запускающий код регистрирует задачи через `WaitGroup.Add` до ожидания.
2. Каждая горутина отмечает завершение через `defer wg.Done()`.
3. Координатор ждёт все горутины и один раз закрывает канал.
4. Потребитель читает до закрытия. Для пустой партии цикл сразу завершается без записей.

У каждого обработчика есть право отправлять. Если отдельный обработчик закроет общий выход, другие ещё могут попытаться отправить туда. Поэтому право закрытия принадлежит одному координатору.

Канал небуферизированный. Если потребитель медленный, отправитель ждёт. Для небольшой партии в этом уроке создаётся горутина на каждый вход. Для большого потока можно оставить ту же структуру результата и заменить запуск на пул или ограничить число допущенных задач.

## 5. Ошибки задач и отмена партии

Ошибка задачи передаётся через `Result.Err`. Остальные задачи продолжают работу. Если нужен режим остановки по первой ошибке, потребитель может вызвать `cancel()` при получении ошибки и дать остальным участникам завершиться.

В последнем примере результат с индексом 0 приходит сразу. Другие обработчики ждут сигнал отмены. Потребитель сохраняет первый результат, отменяет контекст и дочитывает выход только ради подтверждения, что все горутины вышли. Поздние результаты этого примера намеренно игнорируются. В другой программе можно сохранить и их, если выбранная политика это допускает.

Если после отмены готовы и отправка, и ветка `ctx.Done()`, `select` может выбрать любую из двух веток. Следовательно, для частичных результатов нужно заранее договориться, что именно считать частью снимка. Переданный в обработчик контекст позволяет ему остановиться кооперативно. Обработчик, который игнорирует отмену и блокируется навсегда, задержит закрытие результата.

## Ожидаемый вывод

```text
=== 1. Arrival order ===
First arrival: index=1 value=20
Next arrival: index=0 value=10

=== 2. Input order with errors ===
Index 0: value=6 error=<nil> received=true
Index 1: value=0 error=<nil> received=true
Index 2: value=0 error=negative input received=true
Index 3: value=6 error=<nil> received=true

=== 3. Empty batch ===
Entries: 0

=== 4. Keep a partial result ===
Kept index 0: value=0; other entries not retained
```

## Что проверяют тесты

Проверки обнаруживают пропущенные и повторные индексы, потерю ошибки отдельной задачи, смешение нуля и отсутствующей записи, зависание пустой партии и запуск обработчика после предварительной отмены. Отдельный тест с `testing/synctest` дожидается блокировки отправителей и отменяет поток, пока выход никто не читает. Так дочитывание случайно не маскирует ошибку в ветке отмены.

Сбор результатов ограничен одним таймером на две секунды. Флаг `-timeout 10s` ограничивает весь запуск пакета.

## Попробуй самостоятельно

1. Добавь несколько нулей и одинаковых отрицательных входов. Проверь, что каждый индекс сохранился.
2. Реализуй сортировку результатов по индексу после потокового чтения. Когда она удобнее заранее выделенного слайса?
3. Верни политику отмены после первой ошибки. Какие результаты допускается сохранить?
4. Поставь семафор перед запуском горутин и проверь, что формат `Result` остаётся прежним.
5. Добавь отдельные состояния «не началась», «началась» и «завершилась». Где безопаснее обновлять каждое из них?

### 2. Вывод кода

Какие индексы первыми выведет `completionOrderExample` и что гарантирует этот порядок?

<details>
<summary>Показать ответ и объяснение</summary>

Сначала `1`, затем `0`. Задача с индексом 0 ждёт закрытия сигнального канала, а потребитель закрывает его только после чтения первого результата.

</details>

### 3. Вывод кода

Какие пары `(Value, Received)` выдаст `inInputOrder(3, results)`, если перед закрытием пришли только `Result{Index: 2, Value: 6}` и `Result{Index: 0, Value: 0}`?

<details>
<summary>Показать ответ и объяснение</summary>

По порядку индексов получим `(0, true)`, `(0, false)`, `(6, true)`. Запись с индексом 1 остаётся нулевой структурой. Проверка `Received` отличает её от доставленного нуля.

</details>

### 4. Типичная ошибка

Означает ли `Received == false`, что для этой задачи не вызывался `work`?

<details>
<summary>Показать ответ и объяснение</summary>

Нет. `Received` говорит только о доставке результата. Обработка могла завершиться, а отмена могла помешать отправке. Чтобы знать, был ли вызван `work`, нужно учитывать это отдельно.

</details>

### 5. Типичная ошибка

Почему `inInputOrder` опасно кормить произвольными результатами из внешнего источника?

<details>
<summary>Показать ответ и объяснение</summary>

Она индексирует слайс напрямую. Отрицательный или слишком большой индекс вызовет панику, а повтор допустимого индекса затрёт предыдущую запись. Для внешних данных проверь границы и уникальность.

</details>
